## 二、关键事实核对

### 1. 期望难度 = PoW 上限（PowLimitBits）

`524287999 = 0x1f3fffff`，正好是 `PowLimitBits`（`chaincfg/sugar_params.go:40`）。

### 2. 拒绝信息来自哪里

`netsync/manager.go`（约 1480-1487 行）在 `ProcessBlock` 返回 `ErrDifficulty` 时打印：
`block difficulty of X is not the expected value of Y`。

该错误产生于 `blockchain/validate.go`（`CheckBlockHeaderContext`，约 745-770 行），
内部调用 `calcNextRequiredDifficulty`（`blockchain/difficulty.go:178`）。

### 3. 难度算法（SugarShield-N510）

`blockchain/difficulty.go:192-205`，**每块重算**，取前 **510 块**的 `nBits` 求平均：

```go
var bnTot big.Int
pindexFirst := lastNode
for i := 0; pindexFirst != nil && i < SugarPowAveragingWindow; i++ {
    bnTmp := CompactToBig(pindexFirst.Bits())
    bnTot.Add(&bnTot, bnTmp)
    pindexFirst = pindexFirst.Parent()   // ← 沿父链向上走 510 步
}

// Check we have enough blocks (if not, use PoW limit)
if pindexFirst == nil {
    return c.ChainParams().PowLimitBits, nil   // ← 走不满 510 块 → 返回 PowLimitBits
}
```

**结论：期望难度等于 `PowLimitBits`，说明 510 步祖先回走提前遇到 `Parent() == nil` 而中断** ——
即从被拒区块的父节点（`c80fe06b`，高度 43,786,943）往上走 510 块时，链在某处断了。

### 4. 头部曾经“通过”过同一难度检查

头部同步已到 43,839,414（远超 43,786,944）。头部同步走 `maybeAcceptBlockHeader` →
同样的 `CheckBlockHeaderContext` → 同样的 `calcNextRequiredDifficulty`。

- 头部同步用的标志是 `BFNoPoWCheck`（`netsync/manager.go:1987` 附近）。**它只跳过 PoW 哈希校验，不跳过难度重算检查**（只有 `BFFastAdd` 才跳过，见 `validate.go:754-770`）。
- 因此 `639337f9` 的**头部**在当时通过了难度检查（否则头部同步会拒绝它）。
- 而等**区块本体**到达时，同样的检查却失败。

**同一区块、同一难度算法、同一父哈希，头部通过、区块被拒 —— 唯一变量是祖先链的内存状态在两次检查之间发生了变化。**

## 三、根因定位（高置信度）

### 机制：父链被内存窗口驱逐（evictWindow）切断

节点启用 `headerwindow=50000`（`btcd-runtime.ini`），并有配套的内存窗口逻辑（本 fork 新增）：

- `blockIndex.windowBoundary`：低于边界的节点可被驱逐（`blockindex.go:559`）
- `evictWindow`（`blockindex.go:606-742`）：
  - **驱逐**：`height < headerBoundary` 且不在 bestChainView 且不在 [chainTip-window, chainTip+window] 前沿窗口内的节点，从 index map 删除，并回收 struct。
  - **切断父指针**：遍历剩余节点，`node.parent.height < bound` 时 `node.parent = nil`、`node.ancestor = nil`（`blockindex.go:685-705`）。
    - bestChainView 内节点 / 前沿窗口内节点：`bound = chainBoundary`（= bestChainTip - windowSize）
    - 其余节点：`bound = headerBoundary`（= headerTip - windowSize）
  - **头部同步期间 header tip 领先 bestChain tip 极远**（头部到 43.8M，链尖当时才 ~42.7M），
    大量仅头部存在的节点在每次 flush 时被驱逐/切断。

### 触发链（针对 43,786,944 这个具体位置）

1. 头部同步 13:10-13:11 期间，header tip 一路冲到 43,836,943，而 bestChain tip 大约还在 42.7M。
   - 每次头部批量 flush 都触发 `evictWindow`。
   - `headerBoundary ≈ headerTip - 50000`。头部接近 43.8M 时，`headerBoundary ≈ 43.7M+`。
   - 大量**只有头部、尚未有区块数据**的节点（43,786,xxx 一带）要么被驱逐、要么父指针被切断。

2. `639337f9` 的头部在头部同步时被接受，当时它还是**头部节点**，父链完整（因为头部是顺序处理的）。
   难度检查通过（期望 = 520164195）。

3. 之后窗口继续前移 / 再次 evict，`c80fe06b`（父节点）或其 510 个祖先的 `parent` 被切断。

4. 区块本体 `639337f9` 到达，走 `ProcessBlock`：
   - `process.go:194-226`：若父节点 `LookupNode` 返回 nil（父已被驱逐），走**冷读分支**。
     冷读分支只比对高度上已存哈希来决定是否 `BFNoPoWCheck`，**不重建父链**。
   - `maybeAcceptBlock`（`accept.go:63-84`）：`prevNode = b.index.LookupNode(prevHash)`；
     - 若 prevNode 为 nil → “previous block is unknown” → 转孤儿（日志 16:24:56 大量孤儿与此相关）。
     - 若 prevNode 存在但其 510 祖先链里有节点 `parent == nil`（被切断）→
       `calcNextRequiredDifficulty` 走不满 510 步 → 返回 `PowLimitBits`（524287999）→ 拒绝。

5. **关键细节 `accept.go:120-131`**：如果该块已经存在“仅头部”节点（来自头部同步），
   区块到达后是**复用**该节点（`SetStatusFlags(statusDataStored)`），**不会重建其父指针**。
   若该头部节点在 evict 时父指针已被切断，则复用后 `Parent()` 仍为 nil，
   后续任何以它为父的区块都会卡在难度检查上。

### 为什么恰好卡在 43,786,944 这一个点

- 高度 43,786,944 的父块是 `c80fe06b`（高度 43,786,943）。
- 该区块既是 bestChain 当前 tip，又是头部节点。
- 当 `headerBoundary` 前移到刚好覆盖 43,786,94x 一带时，父指针被切断，但节点因在前沿窗口内未被驱逐、保留在内存中，且区块到达后复用节点不重建父链。
- 于是每次尝试连接 43,786,944 都重新计算难度 → 走不满 510 → 期望 = PowLimitBits → 永远拒绝。
- 由于头部已确认这是主链（父 `c80fe06b` 被 header 链确认），区块合法，但节点内存状态不允许其通过本地校验。

> 说明：`c80fe06b` 在日志里先以孤儿形式出现（16:23:20），随后成为被拒区块的父块，
> 说明它在 43,786,944 处理时确实短暂不在内存索引中（已被驱逐），随后冷读/重建回来时父链不完整。

## 四、修复方案（已实施：2 + 3 + 1 三层组合）

| # | 方向 | 说明 | 状态 |
|---|------|------|------|
| 2 | **evictWindow 保护难度窗口** | `blockindex.go` 新增 `difficultyProtectDepth = SugarPowAveragingWindow + medianTimeBlocks`（510+11=521）；`evictWindow` 计算边界后整体下移该深度（低于 `boundary-521` 才驱逐/切断）。保证**任何留在内存索引中的节点，其难度回走所需的 521 层祖先链始终完整**，从源头避免"头部节点父链被切断"。内存代价：每窗口多保留约 521 节点，可忽略。 | ✅ 已实施 |
| 3 | **accept.go 复用头部节点时重建父指针** | `maybeAcceptBlock` 复用已有头部节点（`newNode != nil`）时，若 `newNode.parent == nil` 且 `prevNode != nil`，补设 `newNode.parent = prevNode` 并重建 `ancestor`（`buildAncestor`）。修复"头部节点父指针被切断后区块到达、复用节点不重建父链"的关键嫌疑点。 | ✅ 已实施 |
| 1 | **难度回走遇 nil 时冷读补齐（共识层兜底）** | `coldread.go` 新增 `BlockChain.repairDifficultyChain`：沿不可变的 `parentHash` 从冷索引（`materializeColdNode`）补齐被切断的父链，链式回走至 521 层或遇到存活链接为止；`difficulty.go` 的 `calcNextRequiredDifficulty` 在回走前调用（`c.(*BlockChain)` 类型断言，其他 `ChainCtx` 实现不受影响）。**即使 2/3 有遗漏，难度计算也不会再因内存状态假拒绝合法区块**；冷读失败时保持原行为（返回 `PowLimitBits`）。 | ✅ 已实施 |
| 4 | **临时关闭/调大 headerwindow** | `btcd-runtime.ini` 中 `headerwindow=50000`。仅诊断/救急用，**修复后无需改动**：方案2 已保证难度窗口完整，不必靠调大窗口绕过问题。 | 未采用（无需） |

**安全性说明**：方案1 沿 `parentHash`（头部字段，不可变）从哈希键控的区块索引冷读，读到的是与网络共识完全一致的同一父链；修复只**新增**父指针、从不改写或删除，且仅在链锁（写）下执行——唯一另一处父指针写入者 `evictWindow` 同样在链锁下经 `flushToDB` 运行，二者不可能并发。材料化的冷节点为普通堆分配（非对象池复用），不会与驱逐回收产生悬垂指针。

**编译验证**：`go build ./blockchain/...` 与 `go vet ./blockchain/` 均通过。
