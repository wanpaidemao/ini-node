# ini-node 挖矿上链问题 · 可行修复方案

- 日期：2026-08-27
- 状态（2026-08-30 对代码核实）：**P0、P1-2、P1-3 已实施**；**仅 P1-1（header 链参照自动切换）未实现**，P2/P3 未实施（可选）。逐项见 §5 表。
- 背景：本地挖出 `a23e7e62`（44060189）被持久化为 best-chain tip，网络主链 44060190+ 全部成孤儿、block 卡死、挖矿上不了链。经 umami vs ini-node 对比（`../bug/umami-vs-ini-node-block-processing-20260827.md`）确认：**共识规则两边完全一致**，问题根因在 ini-node 的**链状态机**（无外部锚点 + 先连后存 + 孤儿池），结构性差异见对比文档 C1/C5/第 10 章。
- 本文给出分层修复方案：P0 已实施 / P1 核心加固 / P2 稳健性 / P3 外部锚点，每项含方案、改动位置、风险、验证。

---

## 0. 问题根因回顾（一句话）

本地挖的分叉块占住 best-chain tip（且被持久化），ini-node 没有"网络主链自动胜出"的机制（umami 的 `FindMostWorkChain` + 检查点 + assumevalid 都没有），导致网络主链块连不上 → 全孤儿 → block 卡死 → 挖矿永远在错 tip 上出块。

## 2. P1 核心加固（建议立即实施）

### P1-1：header 链参照切换主链（根治"网络自动胜出"缺失）

**目标**：模仿 umami `FindMostWorkChain`——让 ini-node 以 **bestHeader 链（网络主链投影）** 为参照，本地 bestChain tip 与 header 链同高度 hash 不一致时，**直接切换到 header 链**，而不是等回滚。

**方案**（blockchain/chain.go 新增方法 + netsync/manager.go 调用）：
```
新增 Blockchain.SwitchToHeaderChainIfDiverged() bool:
  1. bestTip := bestChain.Tip()
  2. headerTip := bestHeader.Tip()
  3. if headerTip == nil || headerTip.height <= bestTip.height: return false
  4. headerNode := bestHeader 链在 bestTip.height 处的节点
  5. if headerNode.hash == bestTip.hash: return false   // 一致，无需切换
  6. // 不一致：本地 tip 是分叉块，header 链是网络主链
  7. InvalidateHeaderChain(headerNode.height) 内部复用现有 bestChain.SetTip + stateSnapshot 重建 + 持久化
  8. return true
```
在 `handleStallSample` 中 P0 检测之前调用（现有 62f2a990/ae4f631e 检测可合并进该流程）。

**改动位置**：`backend/blockchain/chain.go`（新增方法）、`backend/netsync/manager.go`（调用点）。

**风险**：中低——复用已上线且验证过的 `InvalidateHeaderChain` 回退/持久化路径；仅新增"header 链参照"触发条件，不触碰共识规则。header 链必须已推进（本场景满足：44,077,197）。

**验证**：构造分叉 tip 场景（或直接在当前污染状态下重启）→ 断言日志出现切换事件、孤儿消失、block 高度推进。

### P1-2：`CheckConnectBlockTemplate` 补充"prev 必须在网络主链（header 链）上"约束

**目标**：堵住 37a5330d 放宽产生的漏洞——基于本地污染 tip 的挖矿块也被本地接受。

**方案**（blockchain/validate.go）：
```
CheckConnectBlockTemplate 现有检查（prev 在 bestChain 上）之后追加:
  headerNode := b.bestHeader 链在 prevNode.height 处的节点
  if headerNode != nil && headerNode.hash != prevNode.hash:
      return ruleError(ErrPrevBlockNotBest, "template prev is not on the network main chain")
```
即：prev 虽然在本地主链上，但如果 header 链（网络）同高度是另一个 hash，说明 prev 是分叉块，拒绝该模板。

**改动位置**：`backend/blockchain/validate.go` `CheckConnectBlockTemplate`。

**风险**：低——正常同步/挖矿场景 header 链与 bestChain 同高度 hash 一致，不触发；仅分叉场景触发拒绝。需注意 header 链可能因窗口未覆盖该高度（node 为 nil 时跳过检查，保持放宽语义）。

**验证**：分叉 tip 场景下挖矿块提交被拒（`rejected: template prev is not on the network main chain`）。

### P1-3：字节序加固（防 block index 损坏复发）——✅ 已实施

**目标**：消除 chainio.go 中 blockIndex key（BigEndian）与 heightIndex/utxo（LittleEndian）混用隐患，防历史 `0xfffff94d` BAD 行再现。

**方案**：
1. 审计 `chainio.go` 所有 `blockIndexKey`/`cursor.Key()` 读写路径，确保 **BigEndian 严格配对**（写入 2257 行 ↔ 读取 1127/1840/1860 行，当前自洽，确认无遗漏）。
2. 审计所有 `heightIndexBucket` 读写确认统一走 `byteOrder`（LittleEndian）。
3. 新增单元测试：`blockIndexKey` 写入 → `binary.BigEndian.Uint32` 读出回环；`dbPutHeightIndex` → `dbFetchHashByHeight` 回环（含大高度、负数边界）。

**改动位置**：`backend/blockchain/chainio.go`、`backend/blockchain/chainio_test.go`（新增）。

**风险**：低——纯内部存储格式，不改共识、不改网络协议。

**验证**：`go test ./blockchain/...` 通过；重建/重启后 block index 无新损坏行。

## 3. P2 稳健性（建议后续实施）

### P2-1：未上链网络块落盘保存（借鉴 umami SaveBlockToDisk）

**目标**：网络主链块连不上本地污染 tip 时**落盘保存**（而非仅内存孤儿池），父块到位后自动恢复，重启不丢失。

**方案**（blockchain/process.go orphan 分支）：`addOrphanBlock` 之前先 `dbPutBlock` 落盘（含 header 索引标记 `statusHaveData`），孤儿池只保留引用；父块连接后 `processOrphans` 走正常 `maybeAcceptBlock`。

**风险**：中——磁盘占用（需按高度/容量淘汰）、状态标记与现有孤儿池逻辑耦合。**建议**：作为 P2 延后，当前 P0 回滚已恢复同步，此优化属于韧性增强。

**验证**：分叉期孤儿块重启后仍在，父块到位后自动上链。

### P2-2：失败块持久化标记（BLOCK_FAILED_VALID 等价）

**目标**：验证失败的块写入索引 `statusFailed`，重启后不重复校验（防 DoS + 防"重启后重新踩坑"）。

**风险**：中——需定义失败状态与现有 status 标志位兼容；失败判定要与 37a5330d 放宽语义一致（仅共识级失败才标记，模板级失败不标记）。

## 4. P3 外部锚点（可选，较大改动）

### P3-1：MinChainWork / assumevalid

参照 umami 主网锚点（`nMinimumChainWork`=高度 6513497 chainwork、`defaultAssumeValid`=高度 6513497 hash，kernel/chainparams.cpp:124-125）：
- `chaincfg/params.go` 新增 `MinChainWork`、`AssumeValid` 字段
- 主链候选选择/回滚判断中应用 MinChainWork 门槛（拒绝低于该 work 的链）
- assumevalid 加速 IBD（跳过历史块校验）

**风险**：高——涉及链选择核心逻辑，改动面大。**建议**：先加 MinChainWork 门槛（防御价值最高），assumevalid 仅作加速优化可缓。

### P3-2：检查点（Checkpoints）

参照 umami `checkpointData`（chainparams.cpp:172）为主网引入历史检查点（如每 500k 块一个），高度 < checkpoint 的块必须 hash 匹配。

**风险**：高——若检查点数据与真实链不符会拒绝整条链；需先与 umami 主网数据逐块核对。**建议**：作为最后手段，仅在 P1/P2 不足以根治时考虑。
