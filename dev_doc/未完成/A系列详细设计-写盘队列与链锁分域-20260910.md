## 1. A4-3：UTXO 热区 / 预取队列 / 冷区分层 + 分代 flush

### 1.1 现状（代码事实）

- `utxoCache`（backend/blockchain/utxocache.go）：`cachedEntries`（mapSlice 分片 map）+ `dirtyOps`（A4-2 脏集合，与 cachedEntries 锁步维护）+ `totalEntryMemory` + `maxTotalMemoryUsage`（默认 250 MiB，config.go:69 `defaultUtxoCacheMaxSizeMiB`）。
- **读取路径**：`fetchEntries(outpoints)`（utxocache.go:291）——先查 cachedEntries，miss 的批量 `db.View` 读 DB 并回填缓存。**当前是"按需读 + 回填"，没有前瞻预取**。
- **连接路径**：`connectBlock`（chain.go:717）→ `checkConnectBlock` → `view.fetchInputUtxos(b.utxoCache, block)`（utxoviewpoint.go:653）逐块拉输入；`b.utxoCache.connectTransactions(block, &stxos)`（chain.go:1124/1427）登记输出/花费。
- **flush**：`flush(dbTx, mode, state)`（utxocache.go:641）——`FlushRequired`（shutdown/rollback/prune）全量清空；`FlushIfNeeded`/`FlushPeriodic` 增量（cleanCache=false 时遍历 dirtyOps 写盘并保留缓存）。写事务数 ∝ flush 次数；读放大 ∝ 冷读次数。
- **mapSlice.put**（utxocache.go:100）：按 maxEntries 分片，满了新建 map——已有"分片"但无热区/代际语义。

### 1.2 目标与收益

- **热区（内存驻留）**：最近连接的 `chainTip-热区深度..chainTip` 高度窗口内的 UTXO 常驻缓存，flush 不清除；
- **预取队列（前瞻 N 块）**：块下载前沿 `(chainTip, chainTip+maxBlockRequestWindow]` 内**已下载块体**的输入 outpoint 提前批量 `fetchEntries`（只读预热），连接时缓存命中；
- **冷区（DB）**：热区窗口外的条目允许驱逐，miss 走 DB；
- **分代 flush**：flush 时按代（generation）写盘，热区代跳过驱逐。

收益机制：缓存命中率↑、DB 读放大↓、写事务数基本不变但每次 flush 写更少。

### 1.3 详细设计

#### 1.3.1 热区窗口（新字段 + 驱逐保护）

- 在 `utxoCache` 增加 `hotFloor int32`（热区下界高度，链锁内更新）；热区深度常量 `utxoHotDepth`（默认 2000，可 ini 调）。
- `connectTransactions` 登记输出时把 `blockHeight` 写入 entry（`UtxoEntry` 已有 `BlockHeight()`）；`hotFloor = bestTip.Height - utxoHotDepth`。
- **驱逐保护**：`fetchEntries` 与 `connectTransactions` 不改驱逐逻辑；新增**惰性驱逐**——flush 全量清空前检查 `entry.BlockHeight() >= hotFloor` 的条目打 `hot` 标记保留（或直接不清空、仅清 dirtyOps 语义）。实施时在 `writeCache` 的 cleanCache 分支处理。

#### 1.3.2 预取队列（新增函数 + 调用点）

- 新增 `utxoCache.prefetchInputs(block *btcutil.Block)`：解析块输入 outpoint 集合，`fetchEntries` 预热（只读，不改视图、不登记 dirtyOps）。
- **调用点**：`handleBlockMsg` 连接块前（netsync/manager.go，块体已下载、即将 `ProcessBlock`）或 `maybeAcceptBlock` 内 `checkBlockContext` 之后、`connectBlock` 之前——**在链锁内、块连接前**，对下一前沿块（blockDownload 游标 +1..+N）执行。为控制锁内开销，预取按批次、每次最多 N 个 outpoint（`utxoPrefetchBatch`，默认 8192）。
- **数据来源**：块体已在磁盘（`dbStoreBlock` 于 maybeAcceptBlock 已写），`btcutil.NewBlockFromBytes` 或直接 `block.MsgBlock().Transactions` 解析输入。

#### 1.3.3 冷区与分代 flush

- `UtxoEntry` 增加 `generation uint32`（每次 flush 自增）；`writeCache` 增量分支写盘后 `clearModified` 并记录代；全量 flush 时热区代（`>= hotFloor` 的条目）跳过驱逐，冷区代正常清。
- 简化取舍：v1 先只做"热区不驱逐 + 预取"，分代 flush 作为 v2（若 A6 基线显示 flush 写放大仍高再上）。

#### 1.3.4 失效模式与对策

| 失效模式 | 对策 |
|---|---|
| 预取旧视图被应用（reorg 后预取的是旧链输入） | 预取**只填缓存不改视图**；连接仍走原 `fetchInputUtxos` 全量校验；预取条目按 outpoint 缓存，连接时若与链不一致会被原路径覆盖——预取仅是加速，错误预取无副作用（后续 fetchEntries 覆盖） |
| 热区深度过大 → 内存占用上升 | 默认 2000（约 2000 块 × 平均输出数），`hotFloor` 随 tip 前进惰性滑动；A6 内存指标监控 |
| 预取锁内耗时 → 链锁占用 | 批次上限 8192 outpoint；只在块连接前沿预取，且 `prefetch` 内部用 `db.View` 只读事务，与连接事务分离 |
| 与 dirtyOps 冲突（预取的 entry 被 flush 清掉） | 预取只读、不登记 dirtyOps；flush 后预取条目若被清，连接时重新按需读——无一致性风险 |

### 1.4 代码落点清单

| 文件 | 改动 |
|---|---|
| backend/blockchain/utxocache.go | `utxoHotDepth` 常量；`hotFloor` 字段；`prefetchInputs`；`writeCache` 热区保护；generation 字段（v2） |
| backend/blockchain/utxoviewpoint.go | `UtxoEntry` generation（v2）；（预取解析辅助） |
| backend/netsync/manager.go | `handleBlockMsg` 连接前调用 `prefetchInputs` |
| backend/config.go | `utxoHotDepth` / `utxoPrefetchBatch` 可配置默认值 |
| backend/btcd-runtime.ini | 新参数注释 |

### 1.5 验证（A4-3）

1. 测试环境同步 → A6 基线：`fetchEntries` DB 读次数下降（冷读计数），块连接速度不降；
2. 回滚/分叉自愈回归：回滚后预取条目被原路径覆盖，块正确连接；
3. kill -9 随机点重启，UTXO 四线一致；
4. `go test -race` 全绿；`build.bat` 通过。

## 2. A2：链锁分域（回滚 / 连接 / 查询分域锁）

### 2.1 现状（代码事实）

- 单一 `chainLock trackedRWMutex`（blockchain/metrics.go:33，`sync.RWMutex` + 等待计时），保护 BlockChain 绝大部分状态（bestChain、bestHeader、blockIndex、utxoCache、stateSnapshot 等）。
- **使用点分布（全仓）**：
  - 写锁 `Lock()`：chain.go 8 处（CalcSequenceLock、connectBlock、disconnectBlock、FlushBlockIndex、InvalidateBlock、InvalidateHeaderChain、ReconsiderBlock、CachedStateSize）+ accept.go 2 处（maybeAcceptBlock/checkConnectBlock 相关）+ process.go 2 处（ProcessBlock、maybeAcceptBlockHeader）+ validate.go 1 处 + difficulty.go 2 处；
  - 读锁 `RLock()`：chain.go 11 处（BestSnapshot、BestHeader、HeaderHashByHeight、HeaderHeightByHash 等查询）+ chainio.go 3 处（BlocksByHeights 等）+ 其余各文件若干。
- **写路径**：`ProcessBlock`（process.go:165 持写锁）→ `maybeAcceptBlock`（accept.go:273）→ `connectBlock`（chain.go:878）/`disconnectBlock`（chain.go:1021）→ `connectBestChain`（含 reorg）。`InvalidateHeaderChain`/`InvalidateBlock`/`ReconsiderBlock` 是回滚/重试写路径（chain.go:2310/2460/2746）。
- **锁内耗时大户**：connectBlock 的 `db.Update`（index flush + best state + block index + spend journal 同事务，chain.go:764-847）+ 块体 dbStoreBlock（accept.go:170）+ UTXO flush（chain.go:884）。RPC 查询（BestSnapshot 等）与这些写排队。

### 2.2 目标与收益

把单一 chainLock 拆成三个分域锁，跨域只读不互斥：

| 分域锁 | 保护状态 | 写方 | 读方 |
|---|---|---|---|
| **connectLock** | bestChain、bestHeader（连接侧）、utxoCache、stateSnapshot | ProcessBlock/connectBlock/disconnectBlock/connectBestChain | 仅连接路径内部 |
| **rollbackLock** | 回滚专用状态（Invalidate* 的 header 重建、height 索引 purge） | InvalidateHeaderChain/InvalidateBlock/ReconsiderBlock | 查询路径 |
| **queryLock** | 查询用快照（BestSnapshot、BestHeader、HeaderHashByHeight 的视图读取） | 无（只读共享） | 所有 RPC/查询 |

收益机制：回滚与查询不互斥、连接与查询不互斥，锁等待近零，blockHandler 几乎不排队，`getblockchaininfo`/`getblocksyncstatus` 全程无感。

### 2.3 详细设计

#### 2.3.1 分域划分原则（数据归属）

- **只读快照**：`stateSnapshot` 已是**不可变 struct 替换**（chain.go:866-871 注释：旧版本即快照，调用方无需持锁）——查询域读它不需要链锁。这是分域的基础：**查询尽量走快照**，不碰 live 结构。
- **连接域**：bestChain/bestHeader 的连接推进、utxoCache 变更、index dirty 集合——只由 blockHandler 单 goroutine 写（现状已满足），读方只有查询。
- **回滚域**：InvalidateHeaderChain/InvalidateBlock/ReconsiderBlock 对 bestHeader 的重建、DB height 索引 purge——与连接域互斥即可。

#### 2.3.2 锁拓扑（最小改动方案）

- 保留 `chainLock` 作为**连接域锁**（现有 38 处写锁/大部分读锁不动，改动面最小）；
- 新增 `queryLock sync.RWMutex`：查询函数（BestSnapshot/BestHeader/HeaderHashByHeight/HeaderHeightByHash/HeightRange 等）改持 queryLock.RLock；连接/回滚写路径在更新快照前先拿 queryLock.Lock 写快照（瞬时），释放后再继续——查询不再与连接全程排队，只在快照更新瞬间互斥；
- 回滚与连接互斥仍用 chainLock（回滚本身低频，先不复用 queryLock）。

> 说明：**v1 只做"查询与连接/回滚解耦"（queryLock 快照域）**；回滚/连接分域（rollbackLock）作为 v2——因为现状回滚低频、且回滚与连接本就不并发（同一 blockHandler 触发），收益主要来自"查询不等连接写盘"。

#### 2.3.3 查询函数改造清单

- `BestSnapshot()`：返回 `b.stateSnapshot`（原子指针或 queryLock.RLock 读指针）——**已是不可变快照，无需链锁**，直接改读。
- `BestHeader()` / `HeaderHashByHeight()` / `HeaderHeightByHash()`：读 bestHeader 视图（chainView，含内存窗口 + DB 冷读）。v1 用 queryLock.RLock 保护视图读取；连接推进 bestHeader 时 queryLock.Lock 更新（若 bestHeader 视图在链锁内变动，则连接写路径在 chainLock 内套 queryLock 更新视图——瞬时互斥）。
- `LatestBlockLocator()` / `BlockByHeight()` 等其余查询逐一审计：能走快照的走快照，不能的挂 queryLock。

#### 2.3.4 失效模式与对策

| 失效模式 | 对策 |
|---|---|
| 跨域 race：回滚写 bestHeader 与并发查询读视图联动漏审 | `go test -race` 全绿 + 人工构造"查询期间回滚"压测（查询循环 + 后台 InvalidateHeaderChain）；快照更新统一走 queryLock.Lock 写 |
| 查询读到中间态（bestHeader 视图半更新） | 视图更新与快照替换都做成"整指针替换"（原子或 queryLock），不原地改 |
| 连接持 chainLock 又拿 queryLock → 死锁（锁序倒置） | 固定锁序：**chainLock → queryLock**（连接写路径只在这个方向加锁）；查询只拿 queryLock 不拿 chainLock |
| 分域后链锁等待指标失真（chain_lock_wait_ms） | 指标分别统计三把锁（A6 扩展：query_lock_wait_ms / rollback_lock_wait_ms） |

### 2.4 代码落点清单

| 文件 | 改动 |
|---|---|
| backend/blockchain/chain.go | 新增 `queryLock`；BestSnapshot 改快照读；BestHeader/HeaderHashByHeight 等挂 queryLock；连接写路径更新视图处加 queryLock.Lock 写快照 |
| backend/blockchain/metrics.go | 三锁等待统计 |
| backend/rpcserver.go / netsync | 无改动（经既有查询函数间接受益） |

### 2.5 验证（A2）

1. `go test -race ./backend/...` 全绿（重点：查询 × 连接 × 回滚并发）；
2. 人工构造回滚/重组期间持续查询，无 panic/断言失败；
3. A6：`chain_lock_wait_ms` 显著下降、`getblocksyncstatus` 在写盘期 < 1s；
4. 同步 + 回滚回归；kill -9 随机点一致性。

## 3. A3：写盘队列（块体 / 元数据解耦 + 高度水印重放）

### 3.1 现状（代码事实）

- **块体写入**：`maybeAcceptBlock`（accept.go:170）`b.db.Update { dbStoreBlock }`——每块一个独立写事务（块体大、写盘慢）。
- **元数据写入**：`connectBlock`（chain.go:764-847）单个 `db.Update` 事务内完成：`index.flushDirtyLocked`（块索引脏行）+ `dbPutBestTipSnapshot` + `dbPutBestState` + `dbPutBlockIndex`（高度→hash）+ `dbPutSpendJournalEntry`（spend journal）+ `indexManager.ConnectBlock`（可选索引）——**每块一次事务提交，全部在链锁内**。
- **UTXO flush**：`connectBlock` 尾部 `FlushIfNeeded`（chain.go:884）+ 后台周期 `FlushPeriodic`（netsync 触发）。UTXO 一致性状态 `dbPutUtxoStateConsistency`（utxocache.go:626）。
- **崩溃一致性现状**：块体、元数据、UTXO 各自事务；崩溃后靠块索引状态（`statusDataStored`/`statusValid`）与 UTXO 一致性标记恢复。写事务数 ∝ 块数（每块 ≥2 事务：块体 + 元数据）。

### 3.2 目标与收益

- **解耦**：块体写入（重 I/O）与元数据/UTXO 写入（轻 I/O）拆开，各自独立队列；
- **合并写**：元数据 N 块合并为一次写事务（`blockFlushBatchSize`，默认 32），写事务数 ÷32；
- **水印重放**：持久化"已落盘元数据的最高高度水印"，崩溃后从水印重放未落盘块（块体已在磁盘），不丢状态、不需要全量重建。

收益机制：写事务数 ÷N，写盘期链锁占用消失（锁内只入队不入盘），`getblocksyncstatus` 全程 <1s。

### 3.3 详细设计（v2，2026-09-11 修订）

> **初稿教训（writequeue.go 第一版踩坑，已废弃重写）**：
> 1. `writeItem` 只带块体 → **元数据（index 脏行/best state/spend journal/indexManager）
>    仍在链锁内同步写**，A3 核心目标（写事务数 ÷N、链锁零磁盘 I/O）根本没实现；
> 2. `waitFlushed` 用 `height=-1, block=nil` 哨兵 → `dbStoreBlock(nil)` panic；
> 3. 共享 `batch` 计数器在入队/消费并发下波动不定，无法保证"N 块合并一次"语义。
> 正确设计：**writeItem 携带完整元数据快照，connectBlock 的整个 db.Update 移入队列**。

#### 3.3.1 队列结构（新组件，v2）

- 新增 `writeQueue`（backend/blockchain/writequeue.go）：
  - 有界队列 `chan *writeItem`（容量 `writeQueueCap`，默认 64），满时入队阻塞（背压传导到 blockHandler，天然限速）；
  - `writeItem` 携带**完整元数据快照**（非指针引用——writer 异步执行期间源数据可能已被后续块覆盖/驱逐）：
    ```go
    type writeItem struct {
        height      int32                // 本块高度（水印推进基准）
        block       *btcutil.Block       // 块体（重 I/O，dbStoreBlock 入参）

        // 元数据快照（对应 connectBlock 单个 db.Update 内的 6 项写入）：
        nodeRows    []*nodeRowSnapshot   // ① index.flushDirtyLocked 的快照
        bestTipHash chainhash.Hash       // ② dbPutBestTipSnapshot: node.hash
        tipHeight   int32                // ②  dbPutBestTipSnapshot: node.height
        tipWork     *big.Int             // ②  dbPutBestTipSnapshot: node.workSum
        bestState   *BestState           // ④ dbPutBestState: state
        blockHash   chainhash.Hash       // ⑤ dbPutBlockIndex: block.Hash()
        stxos       []SpentTxOut         // ⑥ dbPutSpendJournalEntry: stxos
        // indexManager.ConnectBlock(dbTx, block, stxos) 可由 (block, stxos) 重放，不入快照
    }
    // nodeRowSnapshot = blockNode 的 dbStoreBlockNode 序列化所需字段快照：
    type nodeRowSnapshot struct {
        hash   chainhash.Hash
        height int32
        header wire.BlockHeader // node.Header()
        status blockStatus      // node.status
        // 附带 flushDirtyLocked 中的两个索引行标记：
        hashIndex   bool // dbPutHashIndex(hash, height)
        heightIndex bool // dbPutHeightIndex(height, hash)（bestHeaderView.Contains 时）
    }
    ```
  - **快照生成点（关键设计）**：在 connectBlock 的 `b.index.Lock()` 之后、**原 db.Update 位置**生成快照——把原事务体内的函数调用换成"收集进 writeItem"：
    - 原 `index.flushDirtyLocked(dbTx)` → 遍历 `bi.dirty` 集合，对每个 node 做 `nodeRowSnapshot{hash, height, header: node.Header(), status: node.status, hashIndex: true, heightIndex: bi.bestHeaderView.Contains(node)}`；生成快照后立即 `index.finishFlushLocked(false)` 清 dirty 集（与原行为一致，只是写盘延后）；
    - 原 `dbPutBestTipSnapshot(dbTx, ...)` / `dbPutBestState` / `dbPutBlockIndex` / `dbPutSpendJournalEntry` → 各自的入参（node.hash/height/workSum、state、block.Hash()、stxos）拷入 writeItem；
    - 原 `indexManager.ConnectBlock(dbTx, block, stxos)` → **不入快照**，writer 重放时用 (block, stxos) 重跑。
  - 独立 writer goroutine 串行消费（锁外，只持 db 事务锁）：
    1. 块体落盘 `dbStoreBlock(dbTx, block)`（逐块独立事务，重 I/O 不阻塞连接路径）；
    2. 元数据合并写：累积 `blockFlushBatchSize`（默认 32）个 writeItem 后，**单个 db.Update** 内执行快照的全部写入（nodeRowSnapshot→dbStoreBlockNode+dbPutHashIndex+dbPutHeightIndex、dbPutBestTipSnapshot、dbPutBestState、dbPutBlockIndex、dbPutSpendJournalEntry、indexManager.ConnectBlock）；
    3. 每批次元数据写成功后推进水印 `dbPutWriteWatermark(dbTx, batchMaxHeight)`（**同一事务内**，与元数据原子提交，绝不提前）；
    4. 若队列为空且不足一批，**部分批次也写**（尾部 flush，不丢失），否则重启重放会兜底但增加启动开销。
- **入队点**：`connectBlock` 把原本的 `b.db.Update{...}` 整段替换为"生成 writeItem 快照 + `b.writeQueue.enqueue(item)`"（锁内 O(块内交易数)，**无任何数据库 I/O**）；连接推进仍在内存完成（bestChain.SetTip / stateSnapshot / hotFloor 照旧，且它们已在 queryLock 下交换）。`maybeAcceptBlock` 的 `dbStoreBlock` 也并入同一 writeItem（不再单独事务）。
- **水印**：新 bucket `writeWatermark` 存 `uint32 height`（key "height"）；`dbPutWriteWatermark(dbTx, h)` / `loadWriteWatermark(dbTx) (int32, error)`（无记录返回 -1）。
- **停止流程**：`stop()` 置 `stopped` 原子标志 → 关闭 `stopCh` → **在 writer goroutine 内** drain 剩余队列并 flush 最后部分批次 → 等待 writer 退出后返回；`stop()` 用 `sync.Once` 幂等。**不用 nil 哨兵**（初稿教训：`writeOne(nil block)` panic）。
- **与 UTXO flush 的关系**：UTXO flush（`utxoCache.flush`）仍在链锁内同步执行（A4-2/A4-3 已优化其增量性），不入队列——A3 只搬"块体 + 元数据"，UTXO 保持现状降低风险。

#### 3.3.2 重放路径（崩溃恢复）

- **启动接入点**：`initChainState`（chainio.go:1667）在 `dbFetchBestTipSnapshot`（chainio.go:1772）加载 best-tip 快照、best chain tip 高度 T 确定后，追加 `loadWriteWatermark(dbTx)` 读水印 H；若 `H < T` 则进入重放。
- **重放循环**：对 `(H, T]` 每块：
  - 块体已在磁盘（writer 先落块体再落元数据，故块体必在）→ `dbFetchBlockByHash` 取回；
  - 重建元数据（与正常 writer 相同的写函数）：
    - index 行：从块头构造 `nodeRowSnapshot`（hash/height/header/status=statusDataStored 起始）→ `dbStoreBlockNode` + `dbPutHashIndex` + `dbPutHeightIndex`（高度在主链上时）；
    - best state：`newBestState` 从块重算 → `dbPutBestState`；
    - 高度→hash：`dbPutBlockIndex(dbTx, hash, height)`；
    - spend journal：`connectTransactions(block, view)` 重算（UTXO 视图一致性标记保证 UTXO 已落盘到某高度，重放视图中自该高度起逐块累积）→ `dbPutSpendJournalEntry`；
    - indexManager：`indexManager.ConnectBlock(dbTx, block, stxos)` 重放。
  - 每 32 块合并一次 `db.Update` 写回 → `dbPutWriteWatermark` 推进水印 → 循环结束。
- **重放后**：内存侧 bestChain/bestHeader 视图与 UTXO 缓存照常由 initChainState 的既有逻辑加载（重放只补 DB 元数据，不重复连接）。
- **重放来源**：块体磁盘必在（写序保证）；UTXO 走既有一致性标记恢复（`dbPutUtxoStateConsistency` 已落盘的 hash 之前的 UTXO 视为一致），不做 WAL。
- **v1 取舍**：indexer（可选索引）在重放时由 `indexManager.ConnectBlock` 重放（与正常连接路径一致）；若 indexer 重放复杂，v1 可标注"索引在重放后由 index manager 自愈"。**首版可先只重放 blockIndex 行 + best state + 高度索引**（三个最易重建项），spend journal 重放标注 TODO——测试节点验证四线一致时按实际缺失项补。
- **v1 实际落地（同步自愈替代重放）**：v1 范围是"块体同步存储、元数据异步且与水印同事务原子推进"，因此崩溃后 DB 的一致点**恰好在水印处**——持久化 best state 与水印在同一事务提交，加载出的 tip 永远不会高于水印。启动时**无需重放**：同步机制从水印高度恢复，重新连接已在磁盘的块体，自动重新生成缺失的元数据行。`initChainState` 在加载完成后读取水印并记录日志（`A3: write watermark N below loaded tip M` 表示元数据尾部将由同步重连补齐）。完整重放循环留到 v2（块体也异步化后，届时水印与 best state 不再同事务、才需要重放）。

#### 3.3.3 与 A2 的衔接

- A3 依赖 A2 的锁域边界：快照生成在连接域锁内（chainLock，快、无 I/O），writer goroutine 落盘**不持链锁**（只持 db 事务锁）；
- 查询在落盘进行时读内存状态（连接已推进）——返回"已连接"状态，落盘仅影响崩溃恢复；
- RPC 需要"已确认落盘"的场景（如 flush/stop 等待）由水印查询支撑。

#### 3.3.4 失效模式与对策

| 失效模式 | 对策 |
|---|---|
| 四线一致错位（状态/UTXO/索引/水印） | 水印只推进到"同一事务内四线都写成功"的高度；每次元数据事务原子提交四线（沿用 connectBlock 单事务内多写模式，只是批量） |
| 崩溃丢尾部（入队未落盘） | 水印重放：重启后从水印重放，块体在磁盘则必可重建元数据；kill -9 随机点 ×100 验证 |
| writer 落后 → 内存/队列积压 | 有界队列满时入队阻塞（背压传导到 blockHandler，天然限速）；A6 监控队列深度 |
| 关闭时未落盘数据 | shutdown 流程：停写入 → drain 队列 → flush 最后批次 → 推进水印 → 关 db（沿用现有 FlushRequired 路径） |
| **快照与 dbTx 语义漂移**（初稿教训：只搬块体、元数据仍在锁内） | writeItem 快照在**原 db.Update 位置**收集（数据来源与旧代码完全一致），writer 只是换了个事务上下文执行；块体与元数据**同队列同序**，写序严格"块体先于元数据" |
| **nil 哨兵/停止竞态**（初稿教训） | 停止流程改为 `stopped` 标志 + `stopCh` + writer 内 drain，不用 nil item 哨兵；`stop()` 幂等（sync.Once） |
