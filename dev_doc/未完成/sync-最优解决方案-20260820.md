## 三、待实施修复详案（最优实现，基于 0.1 已实施代码）

### R1 + A：接收侧 prev 校验参照系修正（P9 根治，含超窗 A）

**问题**：接收侧 `handleParallelHeadersMsg` 用 `HeaderHashByHeight(rng.start-1)` 校验 prev，front 超窗时走 DB 冷读，参照系可能是污染残留（P9）或 not found（A，52422925 会误拒合法领先 range）。

**最优实现**（区分三态，替代当前 52422925 的一刀切拒绝）：

```go
// handleParallelHeadersMsg 接收侧 prev 校验
applied := sm.chain.HeaderHeight()          // 已应用链 tip（内存，干净）
if rng.start-1 > applied {
    // 情形①：参照系尚未应用（front 领先超窗，合法并行）——
    // 不校验、不拒绝：暂存 range 等 front 推进到 start-1 后再应用
    // （应用期 processReadyHeaderRanges 会做 prev 校验，参照系干净）
    rng.headers = headers
    rng.received = true
    sm.processReadyHeaderRanges()
    return
}
// 情形②：参照系已应用（窗口内或冷读）→ 走 52422925 现有校验
expected, err := sm.chain.HeaderHashByHeight(rng.start - 1)
if err != nil || !headers[0].PrevBlock.IsEqual(expected) {
    log.Warnf("Peer %v returned headers that do not extend the range "+
        "starting at %d (or could not be verified) -- ignoring response",
        peer.Addr(), rng.start)
    return
}
rng.headers = headers
rng.received = true
sm.processReadyHeaderRanges()
```

**配套**：应用期 `processReadyHeaderRanges` 对每个 header 用 `LookupNode(prevHash)` 判断（见 R4），错接即丢弃——**校验责任从"接收侧"移到"应用侧"**（应用时 prev 必然已应用或确认不存在，参照系干净）。

### R3：P8 修复——回滚时删除 DB 高度索引旧行

**问题**：`InvalidateHeaderChain` 只标 invalid 不删 heightidx 旧行 → 冷读持续供给污染 hash。

**实现**（`InvalidateHeaderChain` 内，标记 invalid 之后）：

```go
// 删除回滚点以上的 DB 高度索引旧行，冷读不再供给污染 hash。
// 新链应用时会逐批重写这些行（flushDirtyLocked 的 dbPutHeightIndex），删除无副作用。
err := b.db.Update(func(dbTx database.Tx) error {
    for h := rollbackHeight + 1; h <= oldHeaderTip; h++ {
        if err := dbRemoveHeightIndex(dbTx, h); err != nil {
            return err
        }
    }
    return nil
})
```

> 需在 chainio.go 新增 `dbRemoveHeightIndex(dbTx, height)`（删除 heightidx bucket 该高度行），与 `dbRemoveBlockIndex`（删 hash/height 双向）区别——这里只删高度→hash 单向。

### R2：P3 修复——ProcessBlockHeader 失败不误断诚实 peer

**问题**：`processReadyHeaderRanges` 应用失败归罪响应 peer 并断开；本地索引被污染时被断的恰是携带真实链的 peer。

**实现**（在 e264eb5c 的"等待前驱"分支之后，其余规则错误走回退）：

```go
for _, blockHeader := range front.headers {
    _, err := sm.chain.ProcessBlockHeader(blockHeader, headerFlags, false)
    if err != nil {
        var ruleErr blockchain.RuleError
        if errors.As(err, &ruleErr) {
            // 规则错误不一定是 peer 过错（本地索引可能已污染）。
            // 记录该 range 起点 hash 为可疑，回退重下；不断开 peer。
            if hash, e2 := sm.chain.HeaderHashByHeight(front.start); e2 == nil {
                sm.suspiciousHeaders[*hash] = struct{}{}
            }
            log.Warnf("Header range at height %d failed to apply: %v -- "+
                "rolling back header chain", front.start, err)
            sm.rollbackFabricatedHeaderChain()
            return
        }
        // 非规则错误（内部错误）才断开
        front.peer.Disconnect()
        sm.abortHeaderSync()
        return
    }
    sm.progressLogger.SetLastLogTime(time.Now())
}
```

### R4：P10 修复——reissueFrontRange 对 received front 加错接检测

**问题**：`reissueFrontRange` 对 `front.received == true` 直接 return（"it will be applied momentarily"），错接 range 永久占用队首。

**实现**：

```go
case front.received:
    // 已接收但可能错接（prev 不在已应用链上）。应用期若无法应用，
    // 说明错接——重新下发而非永久等待。
    if !sm.headerRangeAppliable(front) {
        log.Warnf("Header range at height %d received but not appliable "+
            "(predecessor not connected) -- re-issuing", front.start)
        delete(hs.ranges, front.start)
        delete(hs.peerRange, front.peer)
        sm.reissueHeaderRange(front.peer, front.start)
        return
    }
    return
```

`headerRangeAppliable`：`front.start == nextHeight` 且 `LookupNode(front.headers[0].PrevBlock) != nil`（prev 已应用）。

### R5：P11 修复——reconnectStoredBlocks 排除孤儿池假阳性

**问题**：`HaveBlock`（含孤儿池）返回 true 但 `FetchBlockByHash`（仅 DB 落盘）失败 → 假阳性回退；且被 `blkDownload` 周期调用。

**实现**：

```go
// reconnectStoredBlocks 内
stored, err := sm.chain.BlockStored(hash)      // 新增：仅查 DB 落盘（不含孤儿池）
if err != nil || !stored {
    return
}
```

> 新增 `BlockChain.BlockStored(hash)`：等价于 `blockExists` 的 DB 路径（`dbTx.HasBlock` + `dbFetchHeightByHash`），不含 `IsKnownOrphan`。孤儿块 payload 只在内存、从不写 DB——它们走正常下载流程（peer 送达后连接），不需要 reconnectStoredBlocks 处理。

### C1：延伸失败快速回退（P4 修复）

**问题**：唯一能发现污染的信号（front 响应不延伸）被当噪音忽略，回退靠块侧 10 分钟计时器。

**实现**（`SyncManager` 加 frontUnreachable 计数）：

```go
// handleParallelHeadersMsg：响应无法延伸 front 时（"do not extend"）
// 记录该 peer，连续 3 个不同 peer 都无法延伸 → front 链确实错位
frontUnreachable map[int32]map[string]time.Time  // start → peer → 时间

// handleStallSample：检查 front 不延伸计数
if len(sm.frontUnreachable[frontStart]) >= 3 {
    log.Warnf("Front header range %d unreachable from 3+ peers -- "+
        "fabricated/forked chain, rolling back early", frontStart)
    sm.rollbackFabricatedHeaderChain()
}
```

10 分钟兜底保留。污染循环从 ≥20min 缩到 ~1-2min。

### C2：front range 双 peer 确认（防 unanimous-apply 漏洞）

**问题**：单 peer 响应 front range（无分歧单票立即应用）→ 错位段可进链（P2 根因）。

**实现**（仅 front range 双确认，back range 保持单票）：

```go
// assignHeaderRange：front range（start == nextHeight）双发两个不同 peer
if start == hs.nextHeight && len(hs.peers) >= 2 {
    // 复用 20260819 方案的 votes 机制：front 需 2 个独立 peer 一致首 hash 才应用
}

// handleParallelHeadersMsg：front range 需 2 票；在场 peer < 2 时降级单票（C1 兜底）
```

**防污染强度**：fork 段过不了 front（第二票来自诚实 peer 时 hash 不一致 → 分歧仲裁 → 真实链胜出）。两 peer 同源才可能穿透（概率低）。

1. `go build ./...` + `go vet ./netsync/ ./blockchain/` 通过；

## 五、风险与回退

| 风险 | 缓解 |
|---|---|
| R1+A 的"暂存等待"可能让 back range 缓冲增多 | 只对 `rng.start-1 > applied` 暂存；应用期串行推进，缓冲上限 = 在飞 range 数 × 2000（内存 ~320KB） |
| R3 删 DB 行若与并发 flush 竞争 | 在 `InvalidateHeaderChain` 的 chainLock 内执行，且新链应用逐批重写，无副作用 |
| C2 稀疏网络 front 等待变长 | 在场 peer <2 时降级单票 + C1 兜底（不比现状差） |
| 每步独立提交 | 可单独 revert，互不阻塞 |
