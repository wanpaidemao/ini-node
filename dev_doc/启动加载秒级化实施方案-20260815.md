# 正式实施方案：阶段一启动加载秒级化（best-tip + workSum 快照 + 只加载窗口）

> 制定日期：2026-08-15
> 现状：每次启动 `Loading block index...` 约 12 分钟——`initChainState`（chainio.go:1572）用 cursor 全量遍历 `blockheaderidx` 桶（43.8M 条），逐条反序列化 + 串行链接 + 累积 workSum（~16μs/条，NVMe 下瓶颈是每记录处理开销而非带宽）。
> 目标：启动 12 分钟 → 秒级，同时**消除选错链风险**（快照仅作缓存，DB 永远权威）。

---

## 一、设计总览

```
启动流程（改造后）:
  读快照(best_tip_hash + best_tip_height + best_work_sum)
    ↓
  校验: dbFetchHashByHeight(best_tip_height) == best_tip_hash ?
    ├─ 一致 → 从快照 tip 开始，只加载窗口内节点（headerwindow），快速恢复
    └─ 不一致/无快照 → 回退全量扫描（老路径，12 分钟，最坏=现状）
```

**核心原则：快照只是"读起点坐标"，不提供任何共识事实；共识事实（workSum/难度/hash 有效性）全部从 DB 冷读。**

---

## 二、数据结构

### 2.1 快照键（存于 `blockheaderidx` 桶，与头索引同事务）

```
键:   "\x00best_tip_snapshot"
值:   [32B best_tip_hash] + [4B best_tip_height] + [32B best_work_sum(BigInt 序列化)]
```

- 复用 `blockheaderidx` 桶（chainio.go:40），避免新建桶/迁移
- 用 `\x00` 前缀，与现有键（hash）不冲突

### 2.2 内存字段

```go
// BlockChain 新增（chain.go）
bestTipSnapshot struct {  // 持久化快照（DB）
    hash   chainhash.Hash
    height int32
    work   *big.Int
}
hasSnapshot bool  // 本次启动是否用过快照（用于日志/统计）
```

---

## 三、启动流程改造（initChainState）

### 3.1 读快照

```go
snap, ok, err := dbFetchBestTipSnapshot(dbTx)   // 新函数，读 "\x00best_tip_snapshot"
```

### 3.2 校验（防选错链核心）

```go
if ok {
    mainHash, herr := dbFetchHashByHeight(dbTx, snap.height)
    if herr == nil && mainHash != nil && *mainHash == snap.hash {
        useSnapshot = true   // 快照有效
    }
    // 任何不一致 → useSnapshot = false（回退全量扫描）
}
```

### 3.3 快照路径（秒级）

```go
if useSnapshot {
    // ① 从快照高度开始，加载窗口内节点（最近 headerwindow 条，无需全量遍历）
    //    利用 bestChain 链表反向构建：从 tip 沿 parent 指针回退 headerwindow 条
    // ② workSum 直接用快照值（从 DB 冷读 tip 的持久化 workSum 二次核对）
    // ③ 校验窗口内 tip 与 DB 高度索引一致（逐点抽查 N 个高度比 hash）
    // ④ 构建完成，跳过全量 43.8M 条遍历
} else {
    // 老路径：cursor 全量遍历（现状 12 分钟）
}
```

> **workSum 不直接从快照信任**：快照只给 tip 坐标，`best_work_sum` 字段仅作"提示"，启动时用 `dbFetchBlockNode(tip.hash).workSum`（DB 冷读）作为最终值——快照若被篡改，此步自然对不上（或落回全量扫描）。

### 3.4 快照更新时机（原子写）

```go
// connectBlock / disconnectBlock（含重组）内，与头索引同事务写快照：
dbPutBestTipSnapshot(dbTx, newTip)   // 同一 dbTx，原子
```

- 重组时（disconnect）同步回退快照到新 tip
- 崩溃 → 快照与主库同事务 → 要么都新要么都旧，无不一致窗口

## 四、边界情况与风险消除（完善）

| 场景 | 处理 | 选错链风险 |
|------|------|------------|
| 快照损坏/bit rot | 反序列化失败 → 无快照 → 回退全量扫描 | 无（回退兜底） |
| 快照过期（正常未退出） | hash 校验不匹配 → 回退全量扫描 | 无 |
| 快照被篡改（假 workSum） | workSum 以 DB 冷读为准，快照仅提示 | 无 |
| 快照高度处主链重组 | dbFetchHashByHeight ≠ 快照 hash → 回退 | 无 |
| 窗口与 DB 不一致 | 逐点抽查 N 高度比 hash → 不一致回退 | 无 |
| 首次升级（无快照） | 走全量扫描生成快照（一次性 12 分钟） | 无 |
| 降级回旧版 | 旧版忽略 `\x00` 键（无冲突） | 无 |
| 窗口外共识查询 | 冷读层 materializeColdNode 兜底（已有，需全高度抽查测试） | 低（冷读自身 bug 风险，单独覆盖） |

**结论**：任何校验失败的最坏结果 = 回退全量扫描（现状 12 分钟）——**收益秒级、风险有上限（不劣于现状）**。

## 五、实施步骤

### P1：DB 层（chainio.go）
1. `dbFetchBestTipSnapshot(dbTx)` / `dbPutBestTipSnapshot(dbTx, snap)`（读写 `\x00best_tip_snapshot`）
2. 序列化格式：hash(32B) + height(4B little-endian) + workSum(32B big-endian 定长)

### P2：启动流程（chainio.go initChainState）
3. 读快照 + hash 校验（3.2）
4. 快照路径：从 tip 沿 parent 反向加载窗口节点 + DB 冷读核对 workSum + 逐点抽查
5. 回退路径：保留现状全量扫描

### P3：更新时机（chainio.go connectBlock/disconnectBlock）
6. 两处各加 `dbPutBestTipSnapshot`（同事务）

### P4：验证与测试
7. 全高度抽查测试（随机 N 个高度：窗口恢复后 hash 与 DB 一致）
8. 冷读层全高度抽查（materializeColdNode 对窗口外块正确性）
9. 快照损坏/篡改/过期注入测试（回退路径）
10. 启动时间基准：改造前 12 分钟 vs 改造后（秒级）对比

### P5：收尾
11. 日志：`Block index loaded from snapshot (height X) in Ys` / `snapshot invalid; full scan fallback`
12. 提交 + 推送（`-c http.proxy=`）

| 测试 | 方法 | 通过标准 |
|------|------|----------|
| 正常重启加速 | 连续重启 3 次 | 第 2 次起走快照路径，<10s 完成加载 |

| 升级兼容 | 用旧版跑一段 → 换新版 | 首次全量扫描生成快照，二次启动加速 |
| 共识一致性 | 改造前后 `getblockcount`/`getblockhash` 对比 | 完全一致 |
| 冷读正确性 | 随机 1000 高度冷读 hash 比对 DB | 100% 一致 |

## 七、验证标准（验收）

1. 正常重启：`Loading block index...` 到完成 **<10 秒**（原 12 分钟）
2. 快照损坏/篡改时：自动回退全量扫描，**数据与改造前完全一致**（无选错链）
3. 共识数据（blockcount/hash/difficulty）改造前后一致
4. 三个月内重启 N 次均走快照路径，无一次误判

## 八、风险登记（最终）

| 风险 | 等级 | 缓解 |
|------|------|------|
| 选错链（快照被信任） | 已消除 | 快照仅定位，workSum/hash 全走 DB 冷读 + 校验 + 回退 |
| 冷读层自身 bug | 中 | 全高度抽查测试覆盖（P4-8） |
| 升级一次性成本 | 低 | 首次全量扫描 12 分钟，可接受 |
| 回退路径回归 | 低 | 保留老路径 + 对比测试 |
