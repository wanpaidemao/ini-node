# 后端控制方案：前端全量管理 btcd 节点

> 制定日期：2026-08-15
> 定位：在「前后端整合方案」之上，定义前端对后端节点的**完整控制能力**——RPC 启停、同步/索引暂停、参数分级修改（不重建 / 需重建+双重确认）、监控与数据管理。
> 依赖：方案 A（前端自动拉起/托管 btcd 子进程）为底座；`/api/node-config`（读写 ini）、`/api/index-progress`（重建进度）已就绪。

---

## 一、控制能力总览

| 控制域 | 能力 | 生效方式 | 需重建？ |
|--------|------|----------|----------|
| 节点 | 启动 / 停止 / 重启 | 子进程生命周期 | 否 |
| RPC | 开启 / 关闭 / 端口 / 凭据 | 改 ini + 重启 | 否 |
| 同步 | 暂停（停节点）/ 恢复（重启续跑） | 子进程停/启 | 否 |
| 索引 | 暂停重建 / 恢复重建 / 状态 | 子进程停/启（Init 从 tip 续） | 否 |
| 性能参数 | WriteBuffer/Compaction/BlockCache 等 | 改 ini + 重启 | **否** |
| 结构参数 | sugarindex/txindex/datadir | 改 ini + 重启 | **是（双重确认）** |
| 监控 | 内存/CPU/磁盘/同步速率/peer | 实时轮询 | — |
| 数据管理 | 索引状态、数据目录、清理/备份提示 | 查询 + 操作 | — |

## 二、控制项分级（核心设计）

### 级别 A：热调整（不重启，即时生效）

| 项 | 方式 |
|----|------|
| 日志级别 | btcd `debuglevel` RPC（已存在）→ 前端下拉框 |
| peer 查看 / 断连 | `getpeerinfo` / `disconnectnode`（RPC） |
| 索引/同步状态查看 | `getblockchaininfo` + `/api/index-progress` |

### 级别 B：改 ini + 重启生效，**不重建数据库**

| 参数 | ini 键 | 前端控件 | 说明 |
|------|--------|----------|------|
| RPC 开关 | `rpclisten`（清空=关）/ `norpc=1` | 开关 + 端口框 | 关闭后前端靠 `/api/index-progress` 仍能看到进度 |
| RPC 用户/密码 | `rpcuser` / `rpcpass` | 文本框/密码框 | 改后前端代理自动用新凭据（ini 解析） |
| 明文连接 | `notls` | 复选框 | |
| 数据目录 | `datadir` | 文本框 | ⚠️ 见级别 C（涉及数据搬移，归 C 类） |
| 头部窗口 | `headerwindow` | 数字框 | 内存头部窗口，不重建 |
| 内存缓存 | `dbCache`（MiB） | 数字框 | ffldb 块缓存，不重建 |
| UTXO 缓存 | `utxocachemaxsize`（MiB） | 数字框 | 不重建 |
| 打开文件数 | `openfiles` | 数字框 | 不重建 |
| P2P 端口 | `listen` | 端口框 | 不重建 |
| 最大连接 | `maxpeers` | 数字框 | 不重建 |
| UPnP | `upnp` | 复选框 | 不重建 |
| Profile 端口 | `profile` | 数字框 | pprof，不重建 |
| 同步模式 | `blocksonly` | 复选框 | 只同步不广播，不重建 |
| checkpoint | `addcheckpoint` | 只读展示 | 主链起点校验，建议勿改 |

> 级别 B 修改 → 保存写 ini → 提示「重启节点后生效」→ 用户点「重启节点」→ `host.Shutdown()+EnsureRunning()` → 从 tip 续跑（孤儿判定已修复，不会误重建）。

### 级别 C：改 ini + 重启 + **全量重建数据库**（双重确认）

| 参数 | ini 键 | 影响 |
|------|--------|------|
| 地址索引开关 | `sugarindex` | 关→开触发全量重建（约 4-8h） |
| 交易索引开关 | `txindex` | 开→全量重建交易索引 |
| 数据目录变更 | `datadir` | 数据搬移 + 全新索引 |

**双重确认流程**（前端 UI）：
1. 用户修改 C 类参数 → 点「保存」→ 弹出**第一层确认**：「此修改需要重建索引数据库（约 4-8 小时），确定保存？[取消 / 继续]」
2. 用户选「继续」→ 弹出**第二层确认**：「请再次确认：将重建索引，重建期间节点 RPC 不可用，前端仅显示进度。输入『REBUILD』确认 [确认 / 取消]」——**必须输入关键字才能生效**（防误触）
3. 确认后：写 ini → 重启节点 → 进入重建（前端 Dashboard 显示进度条）

## 三、暂停 / 恢复设计

### 同步暂停
- btcd 无运行时「暂停同步」RPC；等价实现：**前端停子进程**（保留数据，`cmd.Kill()`）→ 状态显示「已暂停」
- 恢复：前端启动节点 → Init 从上次 tip 继续（孤儿判定修复后不会从头重来）

### 索引重建暂停
- sugarindex 重建在 `Init` 内同步执行，无运行时暂停点；等价实现：**停节点即暂停**（tip 已随批量写落盘）
- 恢复：重启节点 → `Init` 从 `indexTip` 继续（progress.json 显示中断高度 → 续跑）

### UI 呈现
```
节点控制:  [启动] [暂停] [重启]    状态: ● 索引重建中 60% (可暂停)
```

## 六、安全与边界

- 前端写 ini **仅白名单键**（B/C 表所列），防注入（`writeIni` 已按行匹配更新）
- C 类双重确认防误触；保存前校验值域（端口 1-65535、数字 ≥0、datadir 路径存在或可创建）
- 暂停节点时若正在写索引，等待当前 batch 落盘再 Kill（或直接 Kill，tip 已随每 100 块落盘，最多丢 100 块索引可重跑）
- RPC 关闭后（`norpc=1`）前端仍可用 `/api/index-progress` 与节点控制；`/rpc` 代理返回明确错误提示
