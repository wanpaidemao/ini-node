# 前后端整合完善方案（单入口 + 完整控制 + 性能设计）

> 制定日期：2026-08-15
> 目标：前端（Wails 桌面应用 `ini-node.exe`）作为**唯一入口**，自动托管 btcd 节点子进程，并提供**完善的后端控制能力**（节点/RPC/同步/索引启停暂停、参数分级修改、监控、数据管理），同时保证**性能与可靠性**。
> 依赖底座：方案 A（前端拉起/托管 btcd）已定；`/api/node-config`（ini 读写）、`/api/index-progress`（重建进度）、Dashboard 进度条已实现。
> 配套文档：`后端控制方案-20260815.md`（参数分级细节）、`前后端整合方案-20260815.md`（基础方案 A）。

## 一、架构总览

```
┌────────────────────────── ini-node.exe (前端, 唯一入口) ──────────────────────────┐
│  Wails WebView2 UI                                                              │
│   ├─ Dashboard: 同步进度 / 重建进度 / 状态                                          │
│   ├─ 后端控制页: 启停/暂停/参数分级/双重确认/监控/数据管理                            │
│   ├─ rpcProxyMiddleware (/rpc → 127.0.0.1:8334)                                 │
│   ├─ /api/node-config (ini 读写·白名单)                                          │
│   ├─ /api/index-progress (重建进度文件)                                          │
│   └─ /api/node-status (进程内存/CPU/磁盘, 不依赖 btcd RPC)                        │
│                                     │                                            │
│  BackendHost (backendhost.go)       │  exec: --configfile --sugarindex=1        │
│   探测 8334 → 拉起/复用 → 退出清理   └──────────────▶ btcd.exe (子进程)            │
└──────────────────────────────────────────────────────────────────────────────────┘
```

**单入口原则**：用户只打开 `ini-node.exe`。启动时探测 `127.0.0.1:8334`：
- 不可连 → 自动拉起 `backend/btcd.exe --configfile=btcd-runtime.ini --sugarindex=1`
- 可连（已有节点/schtasks 方式）→ 复用，不重复拉起
- 退出时 → 仅清理本次拉起的子进程（Kill + Wait 防僵尸）

## 二、功能全景（完善）

### 2.1 节点生命周期控制

| 操作 | 实现 | 说明 |
|------|------|------|
| 启动 | `host.EnsureRunning()` | 探测端口 → 拉起子进程 |
| 停止 | `host.Stop()` | Kill + Wait；tip 已随每 100 块落盘，最多丢 100 块索引可重跑 |
| 重启 | `host.Restart()` = Stop + EnsureRunning | 用最新 ini 生效；从 tip 续跑（孤儿判定已修复，不误重建） |
| 暂停（同步/索引） | `host.Stop()` | 等价暂停；恢复 = 启动（Init 从 indexTip 继续） |
| 状态 | `host.Status()` | 运行中/索引重建中 X%/已停止（PID、进度） |

### 2.2 参数分级修改（核心）

| 级别 | 生效方式 | 是否需要重建 | 前端交互 |
|------|----------|--------------|----------|
| **A 热调** | RPC 即时（debuglevel、peer 断连） | 否 | 下拉/按钮，立即生效 |
| **B 重启生效** | 改 ini + 重启节点 | **否**（索引保留，从 tip 续跑） | 表单编辑 → 保存 → 提示「重启生效」→ 一键重启 |
| **C 重建生效** | 改 ini + 重启 + **全量重建** | **是** | **双重确认**：弹窗①确认 → 弹窗②输入关键字 `REBUILD` 才能保存 |

**B 类参数**（性能/网络，不重建）：`rpclisten`(RPC 开关/端口)、`rpcuser/rpcpass`、`notls`、`headerwindow`、`dbCache`(MiB)、`utxocachemaxsize`(MiB)、`openfiles`、`maxpeers`、`listen`(P2P 端口)、`upnp`、`blocksonly`、`profile`。

**C 类参数**（结构/索引，需重建）：`sugarindex`（地址索引开关）、`txindex`（交易索引开关）、`datadir`（数据目录变更）。

> 完整表格见 `后端控制方案-20260815.md` 第二节。

### 2.3 RPC 服务启停

- 前端「RPC」开关 → 写 `norpc=1`（关）或清空（开）+ 重启（B 类）
- 关闭后 `/rpc` 代理返回明确错误；**前端仍可用** `/api/index-progress`、`/api/node-status` 与节点控制
- 端口/凭据变更后，前端 rpcproxy 从 ini 重新解析（`findIniPath/parseIni`），自动适配新凭据

### 2.4 同步与索引暂停

- btcd 无运行时「暂停同步」RPC → 等价实现：**停子进程即暂停**；恢复启动从 tip 续跑
- 重建索引同理：`Init` 每 100 块落盘 tip，暂停后恢复不重头
- UI：`[启动] [暂停] [重启]` + 状态条（运行中/索引重建中 X%/已暂停/已停止）

### 2.5 监控面板

| 指标 | 来源 | 频率 |
|------|------|------|
| 进程内存/CPU | `/api/node-status`（读进程句柄） | 5s |
| 磁盘占用（index/ 分项） | 数据目录遍历 | 30s |
| 同步速率 | `getblockchaininfo` + 采样 | 5s |
| Peer 数 | `getpeerinfo` | 5s |
| 索引进度 | `/api/index-progress` | 5s |
| 运行时长 | `uptime` RPC / 进程 StartTime | 5s |

### 2.6 数据管理

- 索引状态：tip 高度 / 进度 / 已重建百分比
- 数据目录浏览（只读）+ 占用统计
- 备份提示：改 datadir 或清理前提醒备份
- （远期）索引导出/校验

## 三、性能设计（性能好）

| 关注点 | 设计 | 依据 |
|--------|------|------|
| **启动不阻塞 UI** | `EnsureRunning` 在 `main()` 同步调用但**不等待 RPC 就绪**；索引加载 8-10 分钟期间前端照常打开，显示重建进度 | 重建期 RPC 本就不监听 |
| **日志无阻塞** | 子进程 stdout/stderr 重定向到 `backend/logs/*.log`（文件），**不用管道**——避免管道满时子进程卡死 | 与 schtasks 方式一致 |
| **进度写入低开销** | progress.json 每 **1 万块**写一次（~8s 一次），前端 5s 轮询；文件小（<200B） | 已实现 |
| **通信零中间层** | 前端 rpcproxy 直连 btcd 8334（HTTP Basic Auth），无额外代理进程 | 已实现 |
| **内存可控** | 重建期间节点 ~750MB；前端仅轮询 JSON，无大缓存 | 实测 |
| **并行预取已优化** | sugarindex 重建 4 worker 并行读 + 32 块批量读 + 100 块批量写，~7.2 万块/分钟 | 任务 9 |
| **退出清理** | `OnShutdown` → Kill + Wait，防僵尸；`started` 标记只清理本次拉起的进程 | 防泄漏 |
| **并发安全** | BackendHost 用 `sync.Mutex` 保护 cmd 句柄；探测端口先行防双开 | — |
| **白名单写 ini** | `/api/node-config` POST 仅接受白名单键，防注入 | 安全 |

## 六、风险与边界

- 子进程清理：必须 OnShutdown；Kill 前等待当前 batch 落盘（或直接 Kill，tip 每 100 块已落盘，最多丢 100 块索引可重跑）
- C 类双重确认防误触；值域校验（端口、数字、datadir 路径）
- RPC 关闭后前端降级：靠 `/api/index-progress` + `/api/node-status` 保持可用
- 双开防护：探测端口 + 单实例互斥锁（命名 Mutex）
