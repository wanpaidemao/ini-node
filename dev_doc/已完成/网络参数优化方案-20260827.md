# 网络参数优化方案（P2P 连接数）

> 日期：2026-08-27　范围：backend（btcd 节点）网络层参数　类型：B 类（重启生效，**不触发重建**）
> 状态（2026-08-30 更新）：**已实施**——commit `7561cbc1`（perf(p2p): optimize peer connection limits），
> 当前默认 `defaultMaxPeers = 32`（`backend/config.go:46`）。本文为方案记录。

## 一、背景与问题

当前 P2P 最大连接数默认 **125**（`backend/config.go:46` `defaultMaxPeers = 125`），该值继承自上游
btcd，是为公网全节点设计：通过高冗余度保证全网区块/交易传播。但在**公司/家庭局域网**场景下，125
这个值带来三类实际风险：

1. **上行带宽放大**：Sugarchain **5 秒出一个块**（`backend/chaincfg/params.go:328`
   `TargetTimePerBlock: 5 * time.Second`），比比特币（10 分钟/块）快 120 倍。每个新块经
   `handleRelayInvMsg`（`backend/server.go:2090`）对**每个已连接 peer 单发一份**。连接越多，出向
   带宽放大越狠——一块中继 125 份 vs 8 份，差 15 倍以上。
2. **路由器 NAT 表压力**：全节点在初始同步（IBD）期间频繁连接/断开，产生大量 TIME_WAIT 映射。
   活跃连接上限 125 意味着最多同时 125 条 TCP 连接，加上累计的 TIME_WAIT，廉价办公路由/AP 的
   NAT 表可能被撑爆，表现为全公司网络卡顿。
3. **单 IP 无上限**：`backend/server.go:1945` 是 `TODO: Check for max peers from a single IP`——
   当前代码没有单 IP 连接数限制，LAN 内一台机器（或被攻陷的主机）就能占满全部 125 个槽位，
   挤掉其他节点/钱包，甚至构成日蚀攻击面。

**明确不做**：不改 `sugarindex`/`txindex`/`datadir` 等结构类配置（C 类，改动会触发重新同步），
不动区块数据，不动 RPC 端口等已有 B 类设置。本方案只调网络参数。

## 二、方案

| # | 改动 | 位置 | 效果 |
|---|---|---|---|
| 1 | 默认 `maxpeers`：125 → **32** | `backend/config.go:46` | 总连接预算（inbound+outbound）下降 74%，块/交易中继放大同比例下降 |
| 2 | 新增 `maxpeersperip` 选项（默认 **8**），按 IP 限制 inbound 连接数 | `backend/config.go` + `backend/server.go:1945` | 一台机器最多占 8 个槽位，无法灌满；白名单（`--whitelist`）豁免 |
| 3 | 同步文档与样例配置 | `backend/doc.go`、`backend/sample-btcd.conf`、`backend/README.md` | 默认值说明保持一致 |

### 2.1 maxpeers 默认值 125 → 32

32 的构成：出站槽位（连公网同步，默认约 8 个，`backend/server.go:3459` 预留）+ 入站预算约 24 个
（供内网钱包/节点接入）。仍可通过 `--maxpeers` / ini 覆盖，前端控制台的"最大连接"表单不受影响。

### 2.2 新增 maxpeersperip（默认 8）

- 生效位置：`handleAddPeerMsg`（`backend/server.go:1908`），紧邻现有 `cfg.MaxPeers` 总量检查。
- 规则：**inbound** peer 接入时，统计当前**同 IP 已连接 peer 数**，达到上限即断开新连接；
  `--whitelist` 白名单 peer 豁免（`sp.isWhitelisted`，在接入前已赋值，`server.go:2433`）。
- 校验：必须 > 0，与 `validateMaxPeers` 同风格（`config.go:100`）。
- 默认 8 与 Bitcoin Core 的单 IP 入站上限一致，是久经验证的值。

## 三、效果测算

### 3.1 块中继出向带宽（每 5 秒一个块，每块向每个 peer 单发一份）

| 平均块大小 | 125 peers（现状） | 32 peers（改后） | 降幅 |
|---|---|---|---|
| 100 KB | 2.5 MB/s ≈ 20 Mbps | 0.64 MB/s ≈ 5 Mbps | **-74%** |
| 500 KB | 12.5 MB/s ≈ 100 Mbps | 3.2 MB/s ≈ 26 Mbps | **-74%** |
| 1 MB | 25 MB/s ≈ 200 Mbps | 6.4 MB/s ≈ 51 Mbps | **-74%** |

> 注：实际有 header-first、对方已有 inv 忽略（`server.go:2147`）等优化，上表为上限模型；
> 30 Mbps 上行宽带下，现状 500KB 块即打满，改后余量充足。

### 3.2 交易中继

每笔交易经 `RelayInventory`（`server.go:2636`）逐 peer 单发 inv，放大倍数与连接数成正比：
125 → 32，交易中继出向流量同样 **-74%**。

### 3.3 NAT / 路由器压力

- 活跃连接上限：125 → 32（-74%），IBD 期间累计 TIME_WAIT 映射同比例下降，廉价路由 NAT 表
  被撑爆的概率大幅降低。
- 单 IP 上限 8：一台机器（或一个被攻陷主机）最多占 8 槽，**杜绝单机灌满槽位**的日蚀风险。

## 四、风险与回退

- 均为 B 类参数，改 `ini`/默认值 + 重启即生效，**不重建任何索引**，与现有数据完全兼容。
- 公网环境下 32 个 peer 略低于公网最优冗余（公网建议 64~125），可通过 `--maxpeers` 覆盖；
  内网/公司环境 32 完全够用。
- 若公司内大量钱包/节点从**同一出口 IP**（如云端节点、NAT 汇聚）接入，需要调大
  `maxpeersperip`（如 64），或给内网网段加 `--whitelist` 豁免。
- 回退：把默认值改回 125（或 ini 里显式 `maxpeers=125`）重启即可，无数据迁移。

## 五、验证方式

1. `go test ./...`（backend）：新增/更新单测覆盖 `maxpeersperip` 校验。
2. 根目录 `build.bat` 全量编译，确认 `frontend/bin/btcd.exe` 产出。
3. 运行时验证：节点日志观察入站被拒连接出现
   `Max peers per IP reached [8] for <ip>`，且 `getpeerinfo` 中同 IP 连接数不超过上限。
