### 2. 挖矿块上链判定（2026-08-27 并入自根目录 `代办.md`）

**问题**：
本地节点挖矿挖出的块（如 `a23e7e62c4fb89468736ed81ff80d96b0843c287cb8e5d273c5b3a1eba531318`，高度 44060189）
没有成功上到主链（主网上不存在该块），但节点把它持久化成了 best chain tip（chain state）。

**后果**：
- 重启时，block index 里没有该块的索引行（或该行损坏被跳过），`initChainState` 找不到 chain tip → 启动闪退：
  `assertion failed: initChainState: cannot find chain tip ... in block index`
- 需要回退到主链上真实存在的最高块，让同步机制重新下载缺失的尾部。

**根因**：
- 挖矿块上链判定与 umami 不一致（本地接受了未上主链的块并设为 best tip）。
- 需要核对 `connectBestChain` / `ProcessBlock` 的链选择逻辑，确保只有真正进入主链的块才更新 best chain tip。

**修复方向**：
1. （已完成）`initChainState` 全量扫描改用 block index key 里的真实高度做窗口判断，
   并回退到实际物化的最高节点，避免因 block index 缺行导致启动闪退。
2. （待办）挖矿块上链判定：本地挖出的块若未进入主链，不应成为 best chain tip。
   需与 umami（C++ 参考实现）的链选择行为对齐。
3. （待办）评估是否需要在持久化 chain state 前校验该块确实在最佳链上。

**相关文件**：

### 5. 修改节点用户代理（UserAgent）名称（2026-08-28）✅ 已完成

**问题**：
Umami 客户端显示 ini-node 的节点名称为 `/btcwire:0.5.0/ini:00.00.01/`，不直观。

**根因**：
用户代理由两部分拼接而成：

| 层级 | 文件 | 代码 | 值 |
|------|------|------|-----|
| wire协议库默认值 | `backend/wire/msgversion.go:20` | `DefaultUserAgent` | `/btcwire:0.5.0/` |
| 应用层追加 | `backend/server.go:71,75` | `userAgentName` + `userAgentVersion` | `ini:00.00.01` |
| 拼接函数 | `backend/wire/msgversion.go:254-267` | `AddUserAgent()` | 追加到 `DefaultUserAgent` 后 |

最终结果：`/btcwire:0.5.0/ini:00.00.01/`

其中 `btcwire:0.5.0` 是 btcd wire 协议库的默认标识，所有 btcd 系节点都会带此前缀。Umami 显示的 `/Yumekawa:0.16.3.34/` 是因为它修改了 `DefaultUserAgent` 常量。

**修复方向**：
1. 修改 `backend/wire/msgversion.go:20` 的 `DefaultUserAgent` 常量
2. 修改 `backend/server.go:71` 的 `userAgentName` 和 `server.go:75` 的版本格式
3. 注意：修改 `DefaultUserAgent` 会影响所有使用 wire 库的组件，需评估影响

**相关文件**：
- `backend/wire/msgversion.go`（DefaultUserAgent 常量 + AddUserAgent 函数）
- `backend/server.go`（userAgentName / userAgentVersion 定义）
- `backend/version.go`（appMajor / appMinor / appPatch 定义）

## 五、sugarindex 重建加速参考（2026-08-14 分析，供再次重建时采用）

### 根因摘要（按影响排序）

1. **同步单线程顺序重建**（`sugarindex/indexer.go` `Init`）：逐块串行，无并行
2. **每块一次独立 LevelDB 写事务**（`connectBlock`）：4385 万块 × 每块一次 `Write`
3. **sugarindex 独立 LevelDB 未调参**（`sugarindex/db.go` `openIndexDB`）：仅 BloomFilter(10)，未设 WriteBuffer / CompactionTableSize / L0CompactionTrigger，写放大严重
4. **写入条目总量巨大**：每笔交易每个输入/输出多条记录，全程数十亿条
5. **umami 兼容格式开销**（`putObfuscated`）：XOR 混淆 + 前缀键编码

### 加速建议

| 手段 | 预期收益 | 风险 |
|------|----------|------|
| 调大 `openIndexDB` 的 `WriteBuffer`→64MB、`CompactionTableSize`→64MB、L0 触发→8（对齐 ffldb） | 写放大大幅下降，最直接 | 低（独立库参数） |
| 多块共用 LevelDB Batch（如每 100 块一次 `Write`） | 写频率降 100 倍 | 中（需重构 connectBlock） |
| 关闭 WAL sync（重建场景可容忍） | 每次写省 fsync | 中（崩溃需重来） |
| 多 goroutine 分高度并行 + 结果合并 | 利用多核 | 高（写入顺序需保证） |
