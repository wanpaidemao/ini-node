## 八、sugarindex 重建慢的原因分析（2026-08-14）

### 实测进度

- 15:10 开始，至 16:14 已索引 ~164 万 / 4385.6 万（约 3.7%）
- 速度约 **2.4 万块/分钟** → 全程预计 **约 30 小时**

### 根因（按影响排序，均已查代码）

1. **同步单线程顺序重建**（`sugarindex/indexer.go:86-105` `Init`）
   - `for height := tipHeight+1; height <= bestHeight; height++` 逐块串行
   - 每块执行：`chain.BlockByHeight`（主库按高度读区块）+ `chain.FetchSpendJournal`（读花费日志）+ `connectBlock`（写独立 LevelDB）
   - 无任何并行；三个 I/O 全部串行叠加

2. **每块一次独立 LevelDB 写事务**（`sugarindex/indexer.go:160-185` `connectBlock`）
   - 每个区块构造一个 `leveldb.Batch` → `m.db.Write(batch, nil)` 落盘一次
   - 每块含数百~上千笔交易，每笔交易的每个输入/输出都要写多条 address/unspent/spent 记录
   - 4385 万块 × 每块一次写 = 极高写频率

3. **sugarindex 独立 LevelDB 未调参**（`sugarindex/db.go:33-38` `openIndexDB`）
   - 仅设置 `BloomFilter(10)`，**未设置 WriteBuffer / CompactionTableSize / L0CompactionTrigger**
   - goleveldb 默认 WriteBuffer 仅 **4 MB**；对比主库 ffldb 已调至 64/64/256 MB、L0 触发 8
   - 4 MB memtable → 频繁刷 L0、海量小 SST、频繁 compaction → **写放大严重**（这是相对主库最明显的差距）

4. **写入条目总量巨大**
   - 每笔交易：每个输出写 address delta + unspent，每个输入写 spent 记录，另有 timestamp 索引
   - 全程估计写数十亿条 LevelDB 记录

5. **umami 兼容格式开销**（`sugarindex/db.go` `putObfuscated`）
   - 每次写值做 XOR 混淆 + 前缀键编码，额外 CPU

### 加速建议（若需再次重建时实施）

| 手段 | 预期收益 | 风险 |
|------|----------|------|
| 调大 `openIndexDB` 的 `WriteBuffer`→64MB、`CompactionTableSize`→64MB、L0 触发→8（对齐 ffldb） | 写放大大幅下降，最直接 | 低（独立库参数） |
| 多块共用 LevelDB Batch（如每 100 块一次 `Write`） | 写频率降 100 倍 | 中（需重构 connectBlock） |
| 关闭 WAL sync（重建场景可容忍） | 每次写省 fsync | 中（崩溃需重来） |
| 多 goroutine 分高度并行 + 结果合并 | 利用多核 | 高（写入顺序需保证） |

> 当前重建已在进行（约 30h），不建议中途重启打断；加速项留待下次重建或首次从 0 建库时采用。
