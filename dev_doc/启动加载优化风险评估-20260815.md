# 阶段一（加载区块索引 12 分钟）优化方案：风险与收益评估

> 制定日期：2026-08-15
> 现状：每次启动 `Loading block index...` 约 12 分钟（43.8M 块头索引从磁盘读回 + 串行链接/验证）。
> 目标：缩短启动加载时间，同时评估每个方案的收益与风险。

---

## 一、瓶颈回顾（为什么 12 分钟）

| 环节 | 耗时占比 | 性质 |
|------|----------|------|
| 从 DB 读回数 GB 头索引 + 反序列化 | 大头（~10 分钟级） | IO 密集 |
| 串行链接 + `workSum` 累积 + best chain 判定 | 小头（~几十秒） | 串行依赖，无法并行 |
| 只保留最近 5 万块在内存（headerwindow） | — | 设计如此 |

关键：`workSum`（共识累积值）必须"从头算或存下来"，启动时必须扫全链确认 best tip——除非持久化 best tip + 最终 workSum。

---

## 二、四个方案的风险与收益对比

### 方案 1：只加载窗口 + workSum/best-tip 快照（根本解法）

**思路**：持久化「best chain tip + 最终 workSum」快照；启动直接读快照 + 只加载最近 5 万块窗口，其余按需冷读。跳过全链扫描。

| 项 | 评估 |
|----|------|
| **收益** | 启动 12 分钟 → **秒级**（读回量降 99.9%，省掉全链扫描） |
| **风险** | ① 快照与真实链不一致 → 选错主链（**共识风险，最高**）；② 冷读层（materializeColdNode）必须 100% 正确，否则窗口外块取不到；③ 新增快照表，升级/降级兼容；④ 首次升级需生成快照（一次性成本） |
| **共识风险** | **中-高**（workSum/best-tip 快照若损坏会选错链；但快照由节点自写自读、每次启动校验 hash 链一致性可缓解） |
| **实现复杂度** | 中-高（改 initChainState + 新增快照表 + 冷读正确性验证） |
| **建议** | 首推，但需严格校验：快照 hash 与窗口内 tip 一致性校验，不一致则回退全量扫描 |

### 方案 2：仅 workSum 快照（方案 1 的子集）

**思路**：单独存每块 workSum（或最终 best workSum），启动直接取，跳过逐块累积。

| 项 | 评估 |
|----|------|
| **收益** | 省掉排队算（~几十秒）——**只解决小头**，12 分钟大头（读数 GB）仍在 |
| **风险** | 低（增量逐块更新，天然一致） |
| **实现复杂度** | 中 |
| **建议** | 单独做收益有限；作为方案 1 的一部分实现 |

### 方案 3：NVMe / 内存盘（零代码）

**思路**：把数据目录移到 NVMe SSD 或内存盘（RAM disk），顺序读提速。

| 项 | 评估 |
|----|------|
| **收益** | 12 分钟 → 3-5 分钟（顺序读提速 3-4 倍） |
| **风险** | 无代码风险；硬件成本、数据迁移（42GB blocks + 16GB index 需迁移）；内存盘掉电丢数据（不推荐放持久数据） |
| **实现复杂度** | 0（部署/硬件） |
| **建议** | 零风险折中，立即见效；NVMe 为首选，内存盘仅作临时加速 |

### 方案 4：headerwindow 调大（无效）

**思路**：窗口从 5 万块调大，更多块常驻内存。

| 项 | 评估 |
|----|------|
| **收益** | **几乎为 0**——加载必须扫全链确认 best tip，窗口大小不影响启动耗时；只减少运行期冷读 |
| **风险** | 内存随窗口线性增长（5 万→50 万块 = 内存 ×10，几百 MB → 数 GB） |
| **实现复杂度** | 0（改配置） |
| **建议** | **不解决加载慢**，勿用此方案；如只想减少运行期冷读可小调，但注意内存 |

---

## 三、结论与推荐路径

| 优先级 | 方案 | 收益 | 风险 |
|--------|------|------|------|
| **首选** | 方案 1（窗口 + 快照） | 12 分钟 → 秒级 | 中-高（共识，需严格校验回退） |
| 折中 | 方案 3（NVMe） | 12 分钟 → 3-5 分钟 | 极低（纯硬件） |
| 辅助 | 方案 2（workSum 快照） | 省几十秒（小头） | 低 |
| 排除 | 方案 4（窗口调大） | 无（不解决加载） | 内存风险 |

**推荐组合**：
1. **短期**：方案 3（数据目录迁 NVMe）——零代码、立即见效，作为兜底
2. **中期**：方案 1（best-tip + workSum 快照 + 只加载窗口）——根本解法，但必须实现「快照 hash 校验 + 不一致回退全量扫描」双保险，规避共识风险
3. 方案 2 并入方案 1 实现；方案 4 不用

---

## 四、方案 1 实施要点（若采纳）

- 新增快照表：`best_tip_hash + best_tip_height + best_work_sum`，每次 connectBlock 后更新
- 启动：读快照 → 校验（快照 tip 与 DB 高度索引一致）→ 一致则从快照恢复 + 只加载窗口；不一致则回退全量扫描（老路径）
- 冷读依赖：`materializeColdNode`/`nodeAtHeight` 必须对窗口外块可靠（已有冷读层，验证过）
- 升级兼容：旧库无快照 → 首次启动生成快照（走一次全量扫描，一次性成本）
- 验证：hash 链一致性校验 + 快照损坏回退测试
