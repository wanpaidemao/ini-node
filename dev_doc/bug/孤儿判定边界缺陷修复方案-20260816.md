# 修复方案：孤儿判定边界缺陷（main=<nil> 误判孤儿白重建）

> 制定日期：2026-08-16
> 现象：重启后 `Sugar index tip ... (height 43880356) not on main chain (main=<nil>); rebuilding from scratch`——tip 仅比快照高度高 243 块（本应在窗口内），却被判孤儿，从头重建 43.8M 块（40+ 分钟、内存升到 1.2GB）。
> 根因：孤儿判定依赖**内存窗口**（`BlockHashByHeight` → `nodeAtHeight`），快照路径只加载窗口后，窗口边缘外的 tip 查不到 → `main=<nil>` → 误判孤儿。

---

## 一、根因（已定位）

### 孤儿判定代码（sugarindex/indexer.go Init）

```go
mainHash, herr := chain.BlockHashByHeight(tipHeight)
if herr != nil || mainHash == nil || *mainHash != *tipHash {
    // 判孤儿 → wipeIndex → 从头重建
}
```

### 缺陷链

```
BlockHashByHeight(tipHeight)
  → b.nodeAtHeight(tipHeight)     ← ① 内存 bestChain 窗口优先
  → coldNodeAtHeight(tipHeight)   ← ② DB 高度索引兜底
  → nil                           ← ③ 两者都查不到 → 返回 (nil, errNotInMainChain)
```

**为什么窗口外 tip 查不到**：
- 快照路径只 materialize 了**窗口内**节点（`windowBoundary(snapHeight)` 到 snapHeight）
- sugarindex tip 43880356 **略高于**快照高度 43880113（索引建完后 ConnectBlock 又推进了 243 块）
- 重启时快照窗口覆盖到 43880113±windowSize，但 `nodeAtHeight(43880356)` 依赖的 bestChain 或 DB 高度索引在**最新高度附近**可能未覆盖/未重建 → 返回 nil → `main=<nil>` → 误判孤儿

> 对比：全量扫描路径窗口覆盖全链，tip 一定在窗口内 → 不误判。**快照路径 + 窗口边界** 是缺陷触发条件。

---

## 二、修复方案（核心：孤儿判定改走 DB 高度索引，不依赖内存窗口）

### 方案 A：新增 `MainChainHashByHeight`（推荐）

**思路**：孤儿判定应该问"**DB 高度索引里 tipHeight 处的主链块是谁**"——DB 高度索引是全链权威（每高度一条，不含窗口概念），而非内存窗口。

1. **blockchain 新增导出方法**（chainio.go 或 chain.go）：

```go
// MainChainHashByHeight returns the main-chain block hash at the given
// height directly from the DB height index (not the in-memory window),
// so it works for any height regardless of the header window boundary.
func (b *BlockChain) MainChainHashByHeight(height int32) (*chainhash.Hash, error) {
    var hash *chainhash.Hash
    err := b.db.View(func(dbTx database.Tx) error {
        var herr error
        hash, herr = dbFetchHashByHeight(dbTx, height)
        return herr
    })
    return hash, err
}
```

2. **sugarindex.Init 改用它**：

```go
mainHash, herr := chain.MainChainHashByHeight(tipHeight)
if herr != nil || mainHash == nil || *mainHash != *tipHash {
    // 真孤儿（DB 高度索引也查不到/不符）→ 才重建
}
```

**关键差异**：
- 旧：`BlockHashByHeight` → nodeAtHeight（内存窗口）→ 窗口外 nil → 误判
- 新：`MainChainHashByHeight` → dbFetchHashByHeight（DB 高度索引，全链权威）→ 任何主链高度都能查到 → 只有 DB 确认 tip 不在主链才判孤儿

**`mainHash == nil` 的处理**：DB 高度索引查不到（该高度无主链块）→ 这才是**真孤儿**（tip 高度超出主链/被重组），此时才重建——语义正确。

### 方案 B（保守兜底）：mainHash==nil 时回退全量扫描而非重建

若担心 DB 高度索引也有边界问题，可加一层：`mainHash == nil && herr != nil` 时不判孤儿，而是**回退全量扫描**（走老路径加载，tip 自然在主链）——最坏 = 现状 11 分钟，不白重建。

**推荐 A + B 组合**：A 是根治（DB 高度索引权威），B 是兜底（任何异常都不白重建）。

## 四、验证标准

1. 重启后日志：`Sugar index catching up from height X`（而非 `rebuilding from scratch`）
2. tip 高度接近快照高度时不再误判（本次 43880356 vs 43880113 场景）
3. RPC 就绪后 `getpeerinfo` 显示 `subver: /ini:0.26.2/`（subver 修复一并验证）
4. 内存回落（不再重建 → ~800MB）

## 五、风险

| 风险 | 等级 | 缓解 |
|------|------|------|
| DB 高度索引也未覆盖最新高度 | 低 | 方案 B 兜底：回退全量扫描而非重建 |
| 真孤儿（主链重组）被漏判 | 无 | DB 查不到/不符 → 仍判孤儿重建（语义正确） |
| 改动影响全量扫描路径 | 无 | 只改 sugarindex.Init 判定，不影响 initChainState |
