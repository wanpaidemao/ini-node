## 一、当前架构（实测运行中的完整方案）

### 1.1 总体流程

```
节点启动
  └─ startSync()
       ├─ 有更高 header 的 peer ──► fetchHeaders()：并行 header 下载（多 peer 投票）
       │     └─ header 领先块 ≥ blockSyncStartLead ──► maybeStartBlockSync()
       │           └─ startParallelBlockDownload()：并行块下载（与 header 下载重叠）
       └─ header 已齐 ──► 直接 startParallelBlockDownload()

块连接 bestChain.Height ──推进──► front 块 = bestHeight+1（串行关键路径）
每 30s handleStallSample()：
  ├─ reissueStaleHeaderRanges()（6s 超时 reissue + front 保证在飞）
  ├─ reissueStaleBlockSlices()（30s 无交付 reissue slice）
  ├─ reissueStalledBlockPeers()（30s 无交付清空 peer 在飞集）
  ├─ blkDownload()（周期补发，不依赖块到达触发 —— 修复 1a）
  └─ front 高度 10 分钟不推进 ──► rollbackFabricatedHeaderChain()（修复 2）
```

### 1.2 Header 并行下载（方案 A + dcdbeed8 修订）

| 组件 | 实现 | 位置 |
|---|---|---|
| peer 选择 | sync candidate、随机、按 host 去重、上限 `maxHeaderSyncPeers=8` | `fetchHeaders()` |
| 切分 | 不重叠 range，`sliceLen = MaxBlockHeadersPerMsg(2000)`，按 peer 广告高度截断 | `assignHeaderRange()` |
| 投票 | 按 range 首 header hash 归票；**无分歧时单票立即应用**；有分歧需 `minHeaderConfirmations=2` 个独立 peer 一致 | `handleParallelHeadersMsg()` |
| stale 防护 | 响应首 header 的 prev 必须等于 `HeaderHashByHeight(start-1)`，不等则忽略；**注意：该查询失败时检查被跳过** | 同上 |
| 可疑链拒绝 | `suspiciousHeaders`（上限 100）拒绝已回退过的 hash | 同上 |
| 冲突惩罚 | 同 peer 分歧 ≥2 次 → 剔除 + ban 10 分钟 | `recordHeaderConflict()` |
| 自愈 | `headerRangeStallTimeout=6s` reissue；front range 永远保持有请求在飞 | `reissueStaleHeaderRanges()` / `reissueFrontRange()` |
| 应用失败处理 | `ProcessBlockHeader` 报错 → **断开该 peer + abortHeaderSync 重启** | `processReadyHeaderRanges()` |

### 1.3 Block 并行下载（含 1a/1b/2 自愈修复）

| 组件 | 实现 | 位置 |
|---|---|---|
| 切分 | 不重叠 slice，`sliceLen = maxBlockRequestWindow(8192)/8 = 1024`；请求窗口被限制在 `bestHeight+8192` 内且不超 header tip | `assignBlockSlice()` |
| 在飞控制 | 每 peer 在飞上限 `blockInFlightTarget=200`，低于 `minInFlightBlocks=10` 时补发 | `buildBlockRequest()` / `blkDownload()` |
| front 保护 | front slice 优先发给"最近 30s 内交付过"的 peer；front 无人认领超 30s 允许任意 peer 认领（stall fallback，修复 1b） | `assignBlockSlice()` |
| 自愈 | slice 30s 无交付 reissue 给空闲 peer；peer 30s 无交付清空其在飞集；周期 `blkDownload()` 全空窗也能重新派发（修复 1a） | `reissueStaleBlockSlices()` / `reissueStalledBlockPeers()` / `handleStallSample()` |
| 回退兜底 | front 高度 10 分钟不推进（不论请求池状态）→ `rollbackFabricatedHeaderChain()`：回退到已连接块高度、标 invalid、清全部下载状态、重启同步（修复 2） | `handleStallSample()` + `InvalidateHeaderChain()` |
| 断点续传 | 重启后 `reconnectStoredBlocks()` 连接已存储未连接块 | `reconnectStoredBlocks()` |

### 1.4 关键常量汇总

| 常量 | 值 | 作用 |
|---|---|---|
| `maxHeaderSyncPeers` | 8 | header/块并行下载 peer 上限 |
| `headerRangeStallTimeout` | 6s | header range reissue 超时 |
| `blockSliceStallTimeout` | 30s | 块 slice reissue / front fallback 超时 |
| `blockUnavailableTimeout` | 10min | front 高度不动 → 回退 |
| `minHeaderConfirmations` | 2 | 分歧 range 所需确认票数 |
| `maxBlockRequestWindow` | 8192 | 块请求窗口（防孤儿池泛滥） |
| `blockInFlightTarget` | 200 | 每 peer 在飞块上限 |
| `headerwindow`（ini） | 50000 | 内存 header 窗口（evictWindow） |

## 四、根因分析

### 4.1 主根因：unanimous-apply 漏洞让"合法分叉段"进入 header 索引

`dcdbeed8`（无分歧单票立即应用）的动机是正确的：稀疏网络下等第二票会卡 header 下载。但它打开了一个口子：

```
单一 peer 响应 range R（内容是真实网络上的 stale fork / 错位段）
  │  PoW 合法、prev 链自洽（真实 fork 满足一切 header 校验）
  │  无第二个 peer 对 R 投票（range 不重发就没有第二票）
  ▼
单票 = unanimous → 立即应用 → header 索引从 fork 点开始走错方向
  ▼
下一个 range R+1 的所有诚实 peer 响应首 header prev ≠ 本地（已污染）hash
  → "do not extend the range" → 忽略 → header front 永久冻结
  ▼
块下载只能请求本地 header 索引给出的 hash → fork 段的块网络无人提供
  → front 块停摆 → 10 分钟后 rollbackFabricatedHeaderChain
  ▼
回退到已连接块高度 → 重新下载 header → fork 段被再次单票应用（若 polluter
peer 或同源 peer 再次领到该 range）→ 回到第二步，形成闭环
```

**与 20260819 方案 A 的关系**：A2 的投票只对"有分歧的 range"生效；分叉段的进入路径恰恰是"无分歧"（只有一个 peer 被问到、只有它投票）。方案 B（10 分钟回退）能兜底但检测周期太长，净速度 ≈ 每循环推进块数 / 20 分钟 ≈ 5 bl/s。这正是实测的"高度上升很慢、没有恢复冷读速度"。

### 4.2 污染点定位（本轮实测）

- 块已连接到 302739（00:20:34 倾泻后）→ 302739 以下 header 与网络一致；
- header front 冻结在 345411 → 污染区间在 **(302739, 345410]** 内某处；
- 23:58:04 回退到 287410 后 header 一路重下到 345410 —— 说明污染段在重下过程中**再次进入**（P2 重入闭环的实证）。

### 4.3 放大因素

1. **P3 断开诚实 peer**：`processReadyHeaderRanges` 把"应用失败"归罪于响应 peer 并断开。在本地索引被污染的场景下，被断的恰恰是携带真实链的 peer。peer 越断越少，投票仲裁更难凑齐。
2. **P4 检测周期**：唯一能发现污染的信号（front 响应不延伸）被当作噪音忽略，真正的回退触发依赖块侧 10 分钟计时器。
3. **P6 peer churn**：外部条件。headerSync 每次 peer 掉光就 abort 重建，in-flight 缓存全丢；重建后 front range 发给新 peer，6 秒内掉线就再 reissue，请求成功率和 RTT 都极差。
4. **P5**：front 之上 range 的响应跳过 prev 验证即可投票——这些票在 front 应用时才被 `ProcessBlockHeader` 检验，失败即触发 P3。

## 五、候选方案对比（利弊 / 性能 / 内存）

> 通用背景：链高 4390 万、块小、peer 少（1-6）且不稳定、单 peer 带宽有限。目标是**恢复冷读速度**（header ~500/s、块持续数百 bl/s）同时保住防污染能力。

### C1：延伸失败快速回退（把"do not extend"从噪音升级为证据）

front range 的响应被多个**不同** peer 判为 "do not extend"（连续 N=3 个不同 peer，或累计 M=1 分钟）→ 不再忽略，直接触发 `rollbackFabricatedHeaderChain()`（回退到已连接块高度）。10 分钟兜底保留。

| 维度 | 评估 |
|---|---|
| 防污染 | 不防止进入，**只加速恢复**：污染循环从 ≥20min 缩到 ~1-2min，净速度提升约一个量级 |
| 速度影响 | 正常路径零开销（只在已冻结时加速）；回退更频繁但每次损失仅为未连接段 |
| 内存 | 新增一个计数器/时间戳（几十字节） |
| 改动量 | 小：`handleParallelHeadersMsg` 记录"不延伸的 peer 数"，`handleStallSample` 检查 |
| 风险 | 慢 peer 误伤：用"不同 peer 计数"而非时间可基本规避（3 个不同 peer 都不延伸 = 链确实错位） |

### C2：front range 双 peer 确认（堵住 unanimous 漏洞的入口）

**只有 front range**（决定链方向的那一段）需要 2 个独立 peer 返回一致首 hash 才应用；front 之上的 back range 保持单票快速路径（它们最终要过 front 串行应用，错误会在应用时暴露）。front range 双发（同时发给 2 个 peer）；在场 peer <2 时降级为单票 + C1 兜底。

| 维度 | 评估 |
|---|---|
| 防污染 | **入口拦截**：fork 段过不了 front（第二票来自诚实 peer 时 hash 不一致 → 进分歧仲裁 → 真实链 2 票胜出）。两个 peer 同源才可能穿透 |
| 速度影响 | header 下载本来就是 front 串行的：front 双确认只增加约 1 个 RTT 的等待（peer 并行双发）。back range 不受影响，吞吐不降。peer <2 时降级，不卡死 |
| 内存 | 每 front range 多缓冲一份候选 headers：2000 × ~80B ≈ 160KB，峰值 ≤ 2 份，**可忽略** |
| 改动量 | 中：`assignHeaderRange` 支持 front 双发；`handleParallelHeadersMsg` 对 front 走确认门；`reissueFrontRange` 联动 |
| 风险 | 稀疏网络 front 等待变长（但有降级 + C1 兜底）；实现需处理"两票到达顺序"与 reissue 的交互 |

### C3：块侧真相源（架构反转：header 降级为缓存，块连接是唯一真相）

块下载不再信任本地 header 索引给出的 hash 序列：从 peer 的主链 inv/getdata 流直接拉块（headers-only 改为跟随 peer 宣告），header 仅作本地加速索引。任何块连接失败（prev unknown / 难度不符）→ 立即丢弃该段并换 peer 重拉，检测窗口 = 单块处理时间（毫秒级）。

| 维度 | 评估 |
|---|---|
| 防污染 | **根治**：污染的 header 段永远无法转化为块连接，错误在毫秒级被发现；不再需要 10 分钟回退 |
| 速度影响 | 理论上恢复冷读速度；但并行窗口组织变难（不能再用本地 header 高度切 slice，需按 peer inv 分段），乱序块比例升高 |
| 内存 | 孤儿池压力上升（需依赖 `maxBlockRequestWindow` 限流，机制已有）；整体与现架构相当 |
| 改动量 | **大**：重写块请求路径与 slice 分配逻辑，回归测试面广 |
| 风险 | 一次性引入行为变化多，短期回归风险最高；对 segwit/难度窗口等既有修复的交互需要全部重验 |

### C4：可信锚点（checkpoint 化，把回退损失设上界）

沿用现有 checkpoint 机制思想：把"已连接块高度"做成滚动锚（每次成功连接 N=50,000 块记一个本地锚点），header 污染被发现时只回退到最近锚点而非已连接块高度——与现状等价；或引入外部锚（固定 checkpoint / 多 peer 主链 hash 交叉），锚间污染损失有界。

| 维度 | 评估 |
|---|---|
| 防污染 | 部分：锚点间隔内仍可污染（除非锚来自外部真相源） |
| 速度影响 | 回退损失有界，但检测仍靠 C1/B，**本身不解决检测慢** |
| 内存 | 锚点表（几十 KB），可忽略 |
| 改动量 | 小（本地锚）/ 中（外部锚） |
| 风险 | 外部锚与"无外部依赖"的设计目标冲突；纯本地锚收益有限（现状回退本来就是回到已连接块） |

### C5：响应内容级轻量校验（恢复部分 PoW/难度验证）

对 front range 响应抽查难度序列（SugarShield-N510 的 510 窗口）或恢复 `BFNone` 全量校验。

| 维度 | 评估 |
|---|---|
| 防污染 | **对真实 fork 无效**（fork 的 PoW 与难度同样合法——20260819 文档已实测结论：PoW 校验从 800 h/s 降到 25 h/s 且拦不住 f5d4b789 型污染） |
| 速度影响 | 恢复全量校验 = 回到 25 headers/s，不可接受 |
| 内存 | 无额外 |
| 改动量 | 小（回退 flag） |
| 结论 | **已证伪，仅列出作对比，不推荐** |

### 对比总表

| 方案 | 防污染强度 | 预期净速度 | 内存增量 | 改动量 | 回归风险 |
|---|---|---|---|---|---|
| C1 快速回退 | ★★（只加速恢复） | ~10× 当前（5→50 bl/s 量级） | ~0 | 小 | 低 |
| C2 front 双确认 | ★★★★（入口拦截） | **恢复冷读速度**（header ~500/s，块随带宽） | ≤320KB | 中 | 中 |
| C3 块侧真相源 | ★★★★★（根治） | 恢复冷读速度（并行度重构后） | 与现状相当 | 大 | 高 |
| C4 可信锚 | ★★（损失有界） | 不变（不解决检测慢） | ~几十KB | 小/中 | 低/中 |
| C5 PoW 校验 | ★（对 fork 无效） | 25 h/s（劣化） | 0 | 小 | — |

## 六、推荐方案与实施顺序

**推荐组合：C2（主力）+ C1（恢复加速）+ 现有 B（10min 兜底保留）+ P3 修复**

```
实施顺序：
第 1 步  C1 + P3 修复（小改动，立即把污染循环从 20min 压到 1-2min）
         - handleParallelHeadersMsg：连续 3 个不同 peer 的响应无法延伸 front
           → 记录 frontUnreachable 计数（含 peer 集合）
         - handleStallSample：frontUnreachable 达阈值 → rollbackFabricatedHeaderChain
         - ProcessBlockHeader 失败路径：不再 Disconnect 诚实 peer，
           只 abortHeaderSync + 把该 range 起点 hash 记入 suspiciousHeaders
第 2 步  C2（堵住入口，恢复冷读速度）
         - assignHeaderRange：front range 双发（两个不同 peer）
         - handleParallelHeadersMsg：front range 需 2 票一致才应用；
           在场 peer <2 时降级单票（C1 兜底）
         - reissueFrontRange 适配双发状态
第 3 步  观测期：若 C2 后仍出现同源双 peer 穿透（概率低），
         评估 C3 作为长期架构演进
```

**验收标准**：
1. 全量同步日志中 `Sync progress` 持续 >100 bl/s（无 10 分钟级零速段）；
2. `Rolled back fabricated header chain` 若出现，两次间隔内净推进 ≥10 万块（而非数千）；
3. header front 无长时间冻结（`do not extend` 连续出现 ≤3 次即触发回退）；
4. 诚实 peer 不再因 "previous block is not known" 被断开（该日志消失或仅伴随回退动作）；
5. `go build ./...` + `go vet ./netsync/ ./blockchain/` 通过。

**风险与回退**：C2 的降级路径保证稀疏网络（当前常态）不比现状差；每步独立提交，可单独 revert。

## 九、污染复发实例：回滚自愈闭环与 header front 永久卡死（2026-08-20 14:32 日志分析）

> 实例背景：块高 ~173 万的同步实例（与第八节 09:00 的 613 万进度线非同一实例，
> 应为再次删数据后的全量重同步）。核心区块 `4cfb9d29` 经 sugar.wtf 验证真实高度为
> **1,785,079**，本地高度索引记为 **1,732,009**，错位 **53,070** —— 与
> `handleParallelHeadersMsg` 代码注释中观测过的错位段（offset 53314）同一模式，
> 即第 4.1 节 unanimous-apply 漏洞的又一次实例。

### 9.1 核心结论：本地 block 数据不存在；header 存在但高度索引错位

"Stored block ... failed to connect: block ... does not exist" 的精确来源链路：

```
blkDownload() / startParallelBlockDownload()   // manager.go:856/1087，周期调用
  └─ reconnectStoredBlocks()
       ├─ HeaderHashByHeight(1732009) → 4cfb9d29   // 高度索引命中（错位行）
       ├─ HaveBlock(4cfb9d29) → true                // 孤儿池命中（见下）
       └─ ResumeBlockConnect(hash) → FetchBlockByHash
            ├─ LookupNode / materializeColdNode → 节点可解析   // header 侧存在
            └─ dbFetchBlockByNode → ffldb fetchBlockRow        // 数据桶查无此 hash
                 → "block 4cfb9d29 does not exist"             // ← 日志中这句
```

判定依据（四个代码事实，逐条排除）：

1. "block %s does not exist" 出自 ffldb `fetchBlockRow`（db.go:1235-1243，区块
   **数据桶**查无记录）—— 指该区块的 payload **从未落盘**；
2. 若是 header 不存在，报错会是 "block %s is not known"（chainio.go
   `FetchBlockByHash` 的节点解析失败分支）—— 本例节点解析成功，header 侧存在；
3. `HaveBlock`（chain.go:241-246）= `blockExists || IsKnownOrphan`。排除法：
   - `blockExists` 索引路径要求 `statusDataStored`（blockindex.go:480-486），
     与"数据从未落盘"矛盾；
   - `blockExists` DB 路径的 `hasBlock`（ffldb db.go:1132-1140）与
     `fetchBlockRow` 查**同一个** `blockIdxBucket` —— 若它返回 true，fetch 必然
     成功，与报错矛盾；
   - 因此 **true 只能来自孤儿池**：`4cfb9d29` 被错位高度行指为下载目标后由 peer
     送达，但其真实父块（真实高度 1,785,078）本地未知 → 进孤儿池。孤儿块 payload
     只在内存、从不写 DB → `FetchBlockByHash` 必然失败；
4. `reconnectStoredBlocks` 不只在启动时运行 —— `blkDownload` 每次补发前都会调用
   （manager.go:1087），错位索引下随时可再次触发假阳性回退。

**一句话回答用户问题：是本地 block 数据不存在（从未落盘）；header 不仅存在，
而且高度索引是被污染错位的（真实 1,785,079 被记在 1,732,009）。"local data
inconsistent" 判定字面成立，根因是污染索引让回连逻辑找了一个永远取不到数据的块，
不是磁盘数据损坏。**

### 9.3 header front 永久卡死机理（P8+P9+P10 闭环）

关键数字：front 卡在 1800009，回滚起点 1732009 —— 重启后 96 秒内成功应用
68,000 个 header（约 700 h/s，34 个 range，冷读级速度），随后冻结：

```
回滚后重启，range [1800009..] 下发（此时应用链还在 173 万级爬升）
  │
  ▼ 响应到达，接收侧 prev 校验（handleParallelHeadersMsg，manager.go:2200）：
  │    HeaderHashByHeight(1800008)
  │      ├─ 内存窗口未覆盖（尚未应用到 1800008）
  │      └─ 走 DB 冷读 → 读到回滚前污染链残留的高度索引行 → 返回 2258cfa4（P8）
  │    headers[0].PrevBlock == 2258cfa4 → 校验通过，range 标记 received（P9）
  │
  ▼ 前 34 个 range 依次应用，推进 68,000 header 到 1800008
  │    （当前链在 1800008 的 hash ≠ 2258cfa4 —— 新链与污染链在此处分叉）
  │
  ▼ 应用 range [1800009..]：ProcessBlockHeader 报 prev unknown（2258cfa4 不在索引）
  │    → 被当作乱序竞态，保留 range 等前驱（"waiting for predecessor"）
  │    但 2258cfa4 属于已回滚的污染链，永远不会出现
  │
  ▼ reissueFrontRange（manager.go:2747-2749）：front.received == true → 直接 return
  │    （注释 "it will be applied momentarily" —— 对错接 range 无超时/纠错，P10）
  │
  ▼ header apply 永久冻结在 1800009；块请求窗口以 header tip 为顶 →
    块推进到 1800008 后停摆 → 10 分钟后 blockUnavailableTimeout 再次回滚，
    进入下一轮循环（每轮净损失 ≥10 分钟 + 一次诚实 peer 误断）
```

**与设计意图的区别**：`waiting for predecessor` 分支原本针对"前驱 range 仍在
途中"的瞬时乱序竞态（前驱到达即自愈）。本实例是**陈旧参照系导致的错接**——
两种情况日志完全同形，但后者永不自愈，只能等 10 分钟块侧兜底回滚打断。

| # | 问题 | 严重度 | 证据 |
|---|---|---|---|
| P8 | `InvalidateHeaderChain` 只标 invalid 不删 DB 高度索引旧行 → 回滚后冷读持续供给污染链的 hash | **致命** | 9.3：2258cfa4 经冷读返回并通过接收校验 |

### 9.5 新增修复点 R1：错接 range 的应用期判别

`processReadyHeaderRanges` 在 front range 报 `ErrPreviousBlockUnknown` 时增加
一步判别：

```
取 front.headers[0].PrevBlock 与当前链 HeaderHashByHeight(front.start-1) 比对
（此时 front.start-1 必然已应用、在内存窗口内，不走冷读，参照系干净）
  ├─ 一致   → 真乱序竞态：维持现状（保留 range 等前驱）
  └─ 不一致 → 错接 range：丢弃该 range（delete ranges/peerRange）并重新下发
```

与源头修复的关系（建议都做，均为单点小改）：

- **P8 修复（源头）**：`InvalidateHeaderChain` 回滚时删除回滚点以上的 DB 高度
  索引行（新链应用时会逐批重写这些行，删除无副作用）—— 冷读不再供给污染
  hash，接收侧校验回到正确参照系；
- **R1（应用期兜底）**：无论错接 range 经何种路径进入（含未来其他漏洞），
  应用时即被识别清除，front 不再冻结。
