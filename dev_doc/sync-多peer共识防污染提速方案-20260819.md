# 同步提速 + 防 header 索引污染方案（A+B）

> 日期：2026-08-19
> 状态：**方案设计（待实施）**——本地代码已回退到与远端 ini-node/master（b49ac18c）完全一致
> 背景问题：header 链被伪造/错配 header 污染（f5d4b789 同时出现在 340775 与 403540），导致 front 块块体永远拿不到、同步冻结；恢复 header PoW 校验后又导致同步从 ~800 headers/s 降到 ~25 headers/s。

---

## 〇、根因回顾（决定方案方向）

| 观察 | 结论 |
|---|---|
| f5d4b789 是**真实块**（explorer 确认在 403540，prev=5f9877b9），却同时出现在我们索引的 340775 与 403540 | 不是"顺手造的假 header"，是**真实块乱序 / 分叉链**——PoW 校验无法识别（每个 header PoW 都达标） |
| 污染发生在单一 peer 的 header range 响应被接受进链时（stale 检查在 `HeaderHashByHeight(start-1)` 失败时被跳过） | **单一 peer 的响应可信度不足**——需要一个 peer 之外的第二独立确认 |
| 恢复 `BFNoPoWCheck → BFNone` 后 header 降到 25 headers/s | SugarShield-N510 每块沿 510 祖先重算难度，成本极高；且对"真实块乱序"无效 |

**方向**：不用 PoW 校验防污染（慢且无效），改用**多 peer 交叉验证（P2P 共识）**——这是全节点自有能力，不依赖任何外部服务；同时**恢复 BFNoPoWCheck** 恢复速度。块体侧用**可获取性回退**兜底"所有 peer 被同一实体控制"的极端场景。

## 一、方案 A：header 多 peer 交叉验证 + 恢复 BFNoPoWCheck

### A1. 恢复 header 快速路径（速度）

回退后的远端代码已天然满足（`manager.go`）：

```go
// processReadyHeaderRanges（2095 行附近）
headerFlags := blockchain.BFNoPoWCheck   // IBD 期间跳过 PoW 校验
if !sm.ibdMode {
    headerFlags = blockchain.BFNone
}
```

**无需改动**——之前是我改成了 `BFNone` 才变慢，回退后已是原版。**验收点**：header 同步速度应恢复 ~800 headers/s。

### A2. 同 range 至少 N 个独立 peer 确认（防污染核心，N 可配置）

**确认阈值做成常量，默认 2、可调 3**：

```go
// manager.go 常量区
// minHeaderConfirmations 是应用一个 header range 前需要多少个独立 peer 返回
// 一致链。2 防"单 peer 喂伪造链"（第二独立 peer 即可证伪）；3 额外防"两个
// peer 被同一实体控制"。当前 sugarchain 网络 peer 稀少且掉线频繁（峰值 6-8、
// 经常只剩 2-3），默认 2——调 3 会在 peer 不足时因凑不齐确认而停滞。
minHeaderConfirmations = 2
```

#### 数据结构改动（`manager.go` `headerRange`）

```go
type headerRange struct {
    start      int32
    peer       *peerpkg.Peer
    headers    []*wire.BlockHeader
    received   bool
    assignedAt time.Time

    // A2 新增：多数投票裁决。每个独立 peer 的响应按首 header hash 归票，
    // 某候选 hash 得票 ≥ minHeaderConfirmations 才应用。伪造 peer 喂的 hash
    // 永远凑不齐多数，真实链总能胜出；不依赖"第一份为准"（第一份可能恰好
    // 是伪造的，简单以它为准会把真实链误丢导致停滞）。
    votes map[chainhash.Hash]*rangeVote // 候选 hash → 投票记录
}

type rangeVote struct {
    count   int                       // 投该 hash 的独立 peer 数
    peers   map[*peerpkg.Peer]bool    // 已投票 peer（防同 peer 重复计票）
    headers []*wire.BlockHeader       // 该候选的响应内容
}
```

#### 核心逻辑改动（`handleParallelHeadersMsg`）

当前：收到响应 → 验证 prev 连接 → `rng.received = true` → 应用。

改为（投票归票，按 `minHeaderConfirmations` 裁决）：

```go
// 0) 公共前置：响应必须延长本 range 起点（stale 防护）
if expected, err := sm.chain.HeaderHashByHeight(rng.start - 1); err == nil {
    if !headers[0].PrevBlock.IsEqual(expected) {
        log.Warnf("Peer %v returned headers that do not extend the "+
            "range starting at %d -- ignoring stale response",
            peer.Addr(), rng.start)
        return
    }
}

// 1) 按首 header hash 归票
if rng.votes == nil {
    rng.votes = make(map[chainhash.Hash]*rangeVote)
}
h := headers[0].BlockHash()
v, ok := rng.votes[*h]
if !ok {
    v = &rangeVote{peers: make(map[*peerpkg.Peer]bool)}
    v.headers = headers
    rng.votes[*h] = v
}
if v.peers[peer] {
    return // 同一 peer 重复响应，忽略
}
v.peers[peer] = true
v.count++

// 2) 未达阈值 → 继续等更多独立 peer 投票；达阈值 → 应用该候选
if v.count < minHeaderConfirmations {
    return
}
rng.headers = v.headers
rng.received = true

// 3) 投了其他候选 hash 的 peer 视为冲突（它提供了与胜出链不同的链）
for hash, ov := range rng.votes {
    if hash == *h {
        continue
    }
    for p := range ov.peers {
        log.Warnf("Header range at height %d: peer %v disagreed (hash %v "+
            "vs winning %v)", rng.start, p.Addr(), hash, *h)
        sm.recordHeaderConflict(p)   // 冲突计数
    }
}

sm.processReadyHeaderRanges()
```

#### 无多数时（僵局）的处理

当**所有已投票 peer 的候选都未达阈值**（如仅 2 个 peer 且各投不同 hash）：
- `reissueStaleHeaderRanges` 检测到该 range `len(rng.votes) > 0` 且无任何候选 `count >= minHeaderConfirmations` 且已过 `headerRangeStallTimeout` → **清空 votes、重新分配该 range 给新的空闲 peer**（新 peer 响应加入投票）；
- `reissueFrontRange` 同样在僵局时把 front range 重新发出；
- 若一直凑不齐多数（peer 不足），front 保持不应用、不推进——这是**安全侧**行为（宁慢勿错），等待新 peer 加入后再裁决；极端情况下由方案 B（块体不可获取回退）兜底。

`processReadyHeaderRanges` 的前沿检查从 `!front.received` 改为 `!front.received || len(front.votes) == 0 || 无候选达阈值`（未裁决的 front 不应用）。

#### 确认来源选择（避免等死）

- 每个独立 peer 自然响应都会投票（`reissue` 重发后新 peer 响应同样计票）；
- 若 `headerRangeStallTimeout` 内票数不足（慢 peer 场景），由 `reissueStaleHeaderRanges` 把该 range 重发一个空闲 peer——响应到达即成为额外一票；
- `reissueFrontRange` 不变（front 仍保持有请求在飞）；
- **调 3 的适用条件**：仅当网络存在 ≥3 个可用的独立 peer 时（本网络当前不满足，故默认 2）。

#### peer 冲突惩罚

`SyncManager` 新增 `headerConflicts map[*peerpkg.Peer]int`；同一 peer 冲突 ≥2 次 → 从 header 下载剔除（`dropHeaderPeer`）并短期拉黑（记录 `headerBanUntil`，期间不再加入并行下载）。

### A3. 边界与正确性

| 场景 | 行为 |
|---|---|
| 正常：≥N 个独立 peer 返回一致链 | 首份记录，后续确认累加至 `minHeaderConfirmations` → 应用，速度只多几次 hash 比较 |
| 单 peer 喂伪造链（真实场景） | 其他独立 peer 返回真实链 → hash 不一致 → 拒绝伪造响应 → **污染进不了索引** |
| 所有 peer 被同一实体控制（极端） | A 无法识别（响应一致）→ 由方案 B 兜底 |
| range 重发后旧 peer 迟到响应 | 该 peer 已投过票（`votes[h].peers[peer]` 已存在）→ 忽略（不重复计票，现有逻辑保持） |
| 两个 peer 各投不同 hash（僵局） | 两候选各 1 票均未达阈值 → 不应用、继续等第三 peer 或重发该 range（安全侧：宁慢勿错） |

## 二、方案 B：块体可获取性回退（兜底）

### B1. 检测：front 块体长时间不可获取

`handleStallSample`（每 30s）新增检查：

```go
// front 块（bestHeight+1）的 header 已进链，但块体 N 分钟全 peer 拿不到：
// 要么 peer 端没有该块（伪造链的块在真实网络不存在），要么 prev 不匹配（乱序）。
if sm.blockSyncState != nil {
    best := sm.chain.BestSnapshot().Height
    if hash, err := sm.chain.HeaderHashByHeight(best + 1); err == nil {
        if _, inFlight := sm.requestedBlocks[*hash]; inFlight {
            if sm.blockMissingSince == 0 {
                sm.blockMissingSince = time.Now()
            } else if time.Since(sm.blockMissingSince) > blockUnavailableTimeout {
                log.Warnf("Front block %v (height %d) unavailable from all "+
                    "peers for %v -- suspected fabricated/forked header chain, "+
                    "rolling back", hash, best+1, blockUnavailableTimeout)
                sm.rollbackFabricatedHeaderChain()
            }
        } else {
            sm.blockMissingSince = 0
        }
    }
}
```

新增常量：`blockUnavailableTimeout = 10 * time.Minute`（比 `blockSliceStallTimeout` 大一个量级，避免误伤慢 peer）。

### B2. 回退：撤销伪造 header 段

`rollbackFabricatedHeaderChain()`：

1. **定位回退点**：从 bestHeader 沿 parent 链回走，取第一个"块体已存在且已连接"的高度（`HaveBlock` 且 `bestChain.Contains`）作为回退高度 `rollbackHeight`；找不到则回退到 0（重新全量）。
2. **撤销 header**：调用 `chain.InvalidateHeaderChain(rollbackHeight)`（blockchain 层新增）——把 `rollbackHeight+1..bestHeader` 的节点标记为 `statusInvalid`（`SetStatusFlags(BlockValid)` 取反），并从 `bestHeader` 视图 prune 到 `rollbackHeight`；同步清空 `sm.headerSync`（下次重新 fetchHeaders）。
3. **重置下载状态**：`sm.requestedBlocks`/各 peer `requestedBlocks` 清空、`blockSyncState` 重建（`startParallelBlockDownload`）、`blockMissingSince = 0`。
4. **记录证据**：把回退前的可疑 header hash 记入 `sm.suspiciousHeaders`（上限 100），后续 header 下载遇到同 hash 直接拒绝。

### B3. 关键实现点（blockchain 层新增接口）

`blockchain/chain.go` 或 `blockindex.go` 新增：

```go
// InvalidateHeaderChain marks every header above rollbackHeight as invalid and
// prunes the best-header view back to rollbackHeight.  All in-flight requests
// that reference evicted heights fail naturally on the next lookup.
func (b *BlockChain) InvalidateHeaderChain(rollbackHeight int32) error {
    // 1. walk bestHeader from tip down to rollbackHeight+1
    // 2. for each node: SetStatusFlags(BlockValid) 反向标记 + flush dirty
    // 3. bestHeaderView.pruneBelow(rollbackHeight+1)
    // 4. 保留 difficultyProtectDepth 祖先完整性（复用 evictWindow 的保护思路）
}
```

### B4. 边界与正确性

| 场景 | 行为 |
|---|---|
| 慢 peer（网络抖动） | 10 分钟窗口内块体偶发到达 → `blockMissingSince` 归零，不回退 |
| 真伪造链（块在真实网络不存在） | front 块体 10 分钟全 peer 拿不到 → 回退到最近已连接块 → 重新下载真实链 |
| 真实块乱序（f5d4b789 型） | 块体可获取但 prev 不匹配 → `maybeAcceptBlock` 返回 prev unknown → 连续 N 次 → 同样触发回退 |
| 回退后 peer 又喂同一条伪造链 | `suspiciousHeaders` 拒绝已知坏 hash + 冲突惩罚剔除 → 不再进链 |

### 5.3 根因：block 下载自愈机制缺失（死锁闭环）

```
front 块请求被 Freeing 清空 → 所有 peer requestedBlocks = 0
→ blkDownload 只在「收到块时」触发（manager.go:1758）→ 无块到达 → 永不运行
→ reissueStalledBlockPeers 跳过（条件 len(requestedBlocks)>0 不满足）
→ reissueStaleBlockSlices 无事可做（inFlight=0，无 slice）
→ assignBlockSlice front 守卫：front 不在 flight + lastProgress 陈旧 → return false
→ 永久死锁：没有任何代码路径重新请求 front 块
```

**B 方案检测盲区**：旧逻辑 `if _, inFlight := sm.requestedBlocks[*hash]; inFlight` 要求 front 块在请求池中——但死锁状态下 front 已被 Freeing 清出请求池 → 计时器每 30s 重置 → **rollback 永不触发**。

**为什么出现**：回退到远端 b49ac18c 后，早期实现的 block 侧自愈修复（周期 blkDownload + frontMissingSince 兜底）全部丢失；A+B 方案只加了 header 投票 + header 链回退，未恢复 block 侧自愈，且 B 检测条件与真实死锁形态不匹配。

### 5.4 二次修复（已实施并提交 `0f0e5c20`）

| # | 修复 | 位置 | 作用 |
|---|---|---|---|
| 1a | **周期 blkDownload** | `handleStallSample`：`blockSyncState != nil` 时主动调用 `sm.blkDownload()` | 不再依赖"收到块才触发"——全空窗也能重新派发 |
| 1b | **front 兜底** | `assignBlockSlice` + `blockSyncState` 加 `frontMissingSince/frontMissingHeight` | front 块被清请求且超 `blockSliceStallTimeout` 无人认领后，允许任意 peer 认领 front slice，打破"无 peer 合格 → 永不重发"死锁 |
| 2 | **B 检测改高度推进** | `handleStallSample` + `blockMissingHeight` 字段 | 不再要求 front hash 在 `requestedBlocks` 中，改为 **front 高度 10 分钟未推进** → 触发 `rollbackFabricatedHeaderChain` |

**修复 1 语义**：front 块 30s 无人认领 → 任意 peer 可领取（`stall fallback` Warn 日志可观测）——恢复早期验证过的自愈路径。

**修复 2 语义**：`best != sm.blockMissingHeight` 即计时，高度不变超 `blockUnavailableTimeout`（10 分钟）→ 回退，无论 front 是否在请求池。

### 5.7 实测结论：真正根因是块侧自愈缺失（2026-08-20 定论）

**实测证据**（见 5.2-5.4 与后续观察）：

- 日志中**从未出现任何分歧**（`disagreed=0`、`conflicting=0`、`previously rolled back as fabricated=0`）——这些 Yumekawa/Umami peer 提供的 header 链一致，**多 peer 投票机制（d72c6df3）从未仲裁过真实分歧**；
- 仅有的 2 次 `Rolled back fabricated header chain`（23:58 卡 287410 时）由 **`0f0e5c20` 的"高度推进检测"** 触发，与投票无关；
- 删 data 前后差异的根因是**已有本地数据时的断点续传路径缺陷**（`reconnectStoredBlocks` + `buildBlockRequest` cursor 分支假设本地数据与 header 链一致），删 data 清掉本地块与游标后绕开该缺陷 → 不卡。

**结论（2026-08-20）**：**根因是块侧自愈机制缺失**（`0f0e5c20`），header 投票机制（d72c6df3）与投票修正（dcdbeed8）在真实网络下**从未实际触发**（0 次分歧），且 dcdbeed8 完全依赖 d72c6df3（无 d72c6df3 则 dcdbeed8 无法编译）。

**处置**：**移除投票两笔（d72c6df3 + dcdbeed8），只保留块侧自愈（0f0e5c20）+ 其依赖的 rollback 机制**（`InvalidateHeaderChain`/`rollbackFabricatedHeaderChain`/`blockMissingSince`/`blockMissingHeight`，即 d72c6df3 中与投票无关的部分）。代码回到：header 单 peer 直接应用（原版 BFNoPoWCheck 快速路径）+ block 侧周期 blkDownload / front 兜底 / 高度停滞回退。

## 六、整段错位根因：header 链高度→hash 映射被污染（2026-08-20 补充）

### 6.1 现象：本地把真实链整段错位 53314 高度

10:37:54 触发回退的坏块，经 explorer 交叉验证：

| hash | explorer 真实高度 | 本地 header 链高度 | Prev/Next 一致性 |
|---|---|---|---|
| `0477415f...` | 6760004 | 6706690 | explorer 的 Next=074e5f9a ✅ |
| `074e5f9a...` | 6760005 | 6706691 | explorer 的 Prev=0477415f、Next=07ae2df8 ✅ |
| `07ae2df8...` | 6760006 | 6706692 | explorer 的 Prev=074e5f9a ✅ |

**本质**：本地 header 链把真实链 `[6760004, 6760005, 6760006]` 这一段**整体放到了 `[6706690, 6706691, 6706692]`**——错位 **53314** 高度。错位段内部 prev/next 完全自洽、PoW 全部真实，所以通过了所有 header 校验。

### 6.2 根因：stale 防护在冷读失败时被整体跳过

`handleParallelHeadersMsg` 的 prev 校验（当前代码）：

```go
if expected, err := sm.chain.HeaderHashByHeight(rng.start - 1); err == nil {
    if !headers[0].PrevBlock.IsEqual(expected) {
        // 错配 → 忽略 stale 响应
        return
    }
}
```

**`err == nil` 才校验，`err != nil`（冷读失败）时直接放行！**

- `HeaderHashByHeight(start-1)` 在窗口边界/冷读失败时返回 error（`blockheight %v not found`）
- 此时 **peer 返回的 headers 不做任何 prev 校验就被接受** → 错位段进链
- 错位段 prev 自洽 + PoW 真实 → 后续 header 全部通过 → 本地链从此处开始整体偏移 53314
- 这是 8-19 早上就发现过的"stale 防护有漏洞"（`HeaderHashByHeight` 失败时检查被整体跳过），本次为实证

### 6.3 责任链

| 环节 | 责任 |
|---|---|
| ① peer 链在 670 万附近与真实链错位 | **peer 数据源问题**（Yumekawa/Umami 共享的错位数据，内部自洽但位置偏移） |
| ② 接受时 `HeaderHashByHeight` 失败 → 跳过 prev 校验 | **本地代码漏洞** |
| ③ 错位链段进 header 索引 | 高度→hash 映射被污染（f5d4b789 型复现） |
| ④ blocks 按错位 header 请求块体 | 块体不存在/prev 不匹配 → 卡住 → 触发回退（3fc9452e 自愈） |

### 6.4 为什么多 peer 投票（已移除）也防不住

Yumekawa/Umami peer **共享同一条错位链**（同一实体部署、同一数据源）——投票要求"多个 peer 一致"，它们全都一致（都错），投票检测不到。这也是当初投票机制 0 次分歧的原因之一。

### 6.5 修复方向（治本）

**stale 防护不能因 `HeaderHashByHeight` 失败就跳过**——失败时应视为"无法验证"，拒绝该响应并交由 re-issue 机制换 peer 重发，而不是放行：

```go
// 当前：err 时跳过 → 错位段进链
if expected, err := sm.chain.HeaderHashByHeight(rng.start - 1); err == nil {
    if !headers[0].PrevBlock.IsEqual(expected) { return }
}
// 修复：err 时也拒绝（无法验证 = 不接受）
expected, err := sm.chain.HeaderHashByHeight(rng.start - 1)
if err != nil || !headers[0].PrevBlock.IsEqual(expected) {
    log.Warnf("Peer %v returned headers for height %d that cannot be "+
        "verified against the applied chain -- ignoring", peer.Addr(), rng.start)
    return
}
```

已按 6.5 修复方案实施并提交本地（`backend/netsync/manager.go`，+18/-7）：

## 七、顺序竞态根因：并行 header 下载 prev not known 误断开（2026-08-20 补充）

### 7.1 现象：反复断开循环（"连上即断"）

11:20-11:26 日志实证——所有 peer 连上即断，断开原因完全一致：

```
12:25:45  Re-issuing header range at height 6868747 to peer 24.160.187.156
          by taking over its range at height 6870747        ← re-issue 打乱顺序
12:25:47  Received block header from peer 24.160.187.156 failed header
          verification -- disconnecting: previous block
          d1d33b74... is not known                          ← prev 未应用 → 断开
12:25:47  Lost peer 24.160.187.156（连上即断，反复循环）
```

**关键**：`d1d33b74` 经 explorer 验证真实在 **6868746**（Next=03152cd4、Prev=68bd7ca7），本地 6868745/6868746/6868747 与 explorer 逐字节一致——**本地、explorer、peer 三方数据全部正确**。断开不是数据错，是本地处理顺序竞态过严。

### 7.2 根因：并行下载 re-issue 后 range 乱序 → prev not known → 断开 + abort

```
① 并行分配：ranges = {6868746: [peerA], 6868747: [peerB], ...}
② reissueFrontRange "taking over"：front 6868747 超时
   → 从持 6870747 的 peer 手里抢 → delete(ranges, 6868747) → 重发
③ peer 返回 6868747 的 range，但 6868746 的 range 还在飞（未应用）
④ processReadyHeaderRanges 应用 6868747 时：
   ProcessBlockHeader 报 "previous block d1d33b74 is not known"
   （LookupNode(d1d33b74) = nil，因为 6868746 尚未应用）
⑤ 旧逻辑：断开 peer + abortHeaderSync → 从头重下 → 又遇同一竞态
   → 反复断开循环
```

**本质**：远端原版 `processReadyHeaderRanges` 对 `ErrPreviousBlockUnknown` 的处理是"断开 + abortHeaderSync"——这是**串行下载时代的逻辑**；在**并行分片下载**下，re-issue 后 range 乱序是常态，prev not known 是**暂时顺序问题**，不应断开。

### 7.3 修复（2026-08-20，commit `e264eb5c`）

`processReadyHeaderRanges` 失败分支：`ErrPreviousBlockUnknown` 时保留 range 等待 prev，不断开、不 abort；仅真正校验失败才断开：

```go
_, err := sm.chain.ProcessBlockHeader(blockHeader, headerFlags, false)
if err != nil {
    // 顺序竞态：前一 range 尚未应用（prev not known），不是 peer 过错
    var ruleErr blockchain.RuleError
    if errors.As(err, &ruleErr) &&
        ruleErr.ErrorCode == blockchain.ErrPreviousBlockUnknown {
        log.Warnf("Header range at height %d cannot be applied yet "+
            "(previous block not known): %v -- waiting for predecessor",
            front.start, err)
        return    // 保留 range，等前一 range 应用后下轮重试
    }
    front.peer.Disconnect()
    sm.abortHeaderSync()
    return
}
```

`go build ./...` 通过。新增 `errors` 导入。
