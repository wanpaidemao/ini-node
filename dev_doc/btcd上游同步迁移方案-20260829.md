# btcd 上游同步与迁移方案 v2 / Upstream btcd Sync & Migration Plan v2

> 分析日期：2026-08-29（v1 基础上按"分叉面收敛"思路重写）
> 对比基准：fork 最新（含 f52e705c） vs 上游 btcd master（v0.26.2，快照于 d:\dev\AI\btcd-ref）
> 核心问题：①耦合程度；②未来 btcd 升级好不好迁移；③有没有更好的方案。

## 一、结论速览 / TL;DR

1. **这是 btcd 的完整 fork**：主模块声明就是 `github.com/btcsuite/btcd`，3433 个共同文件中 **54 个被修改**（1.6%），fork 新增 62 个文件。
2. **主节点实际编译面比表面小**：只有「主模块 + replace 的 chaincfg/txscript」吃 fork；wire/btcec/btcutil/v2transport/address 用**模块缓存的上游原版**（go.mod 固定版本），仓库里同名子模块是"休眠 fork"。
3. **更好的方案不是更好的合并，而是"缩小分叉面 + 按需同步"**（本版核心，见 §4-§5）：
   - **放弃"定期追版本"** → 改为**按需 cherry-pick**（btcd 非 Bitcoin Core，无频繁共识/安全升级）；
   - **把 9000 行修改里 ~7500 行"性能自研"压回上游/跟随上游**，只留 ~1500 行**共识必须**的分叉；
   - **机制**用 git subtree / patch-queue / replace 隔离，让剩下的合并不再痛。
4. **迁移难度：中等偏上，但高度集中**，且随"分叉面收敛"会持续下降。
5. 当前 fork 依赖版本与上游完全一致（很"新鲜"），**现在建同步习惯成本最低**。

## 四、更好的方案 / Better Strategy（本版核心）

核心转变：**不是找更好的合并工具，而是让"需要合并的东西"变小，并放弃"定期追版本"这个不必要的目标。**

### 4.1 前提一：按需 cherry-pick，而非定期大合并

- btcd 不是 Bitcoin Core：无频繁共识/安全升级，多数更新是新增 RPC、跟进 BIP、性能优化。
- 已能全量同步、正常出块 → 处于"能用 + 维护"状态。
- **真正需要的上游更新 = 明确想要的 bug/安全修复/特定功能** → 按需 cherry-pick。
- 同步成本从"定期大手术"降为"偶尔小手术"。

### 4.2 前提二：把 9000 行里的非共识部分压回上游

给修改分类（详见 §5 清单）：
- **🔒 共识必须（~1500 行）**：yespower、difficulty、chaincfg 参数、奖励、挖矿块判定、空 witness 兼容——没得选，但点清晰。
- **⚙️ 性能自研（~7500 行）**：parallel sync、header 窗口、冷读、utxo 残留清理、leveldb 调参——**不是共识要求**，是当初为速度自研的。上游有等价实现就跟随，没有则以上游为基础重做。
- **💾 磁盘格式绑定**：chainio/coldread 的 header 索引已与磁盘数据绑死，压回 = 需重新同步/迁移数据，需单独决策。

### 4.3 目标架构：分层最小分叉

```
┌─────────────────────────────────────────────┐
│  btcd 核心库（上游依赖）                      │  ← 升级 = 改 go.mod
│  wire · btcec · btcutil · mempool · peer     │
├─────────────────────────────────────────────┤
│  最小共识 fork（唯一需 merge）≈1500 行        │  ← 共识分叉，保留
│  yespower · difficulty · chaincfg 参数 · 奖励 │
├─────────────────────────────────────────────┤
│  Sugarchain 专属新增（零冲突）                │  ← 新增文件，不碰上游
│  sugarindex · coldread · RPC 扩展 · cmd 工具  │
└─────────────────────────────────────────────┘
```

### 4.4 机制升级（替代裸 merge）

1. **git subtree**：`git subtree pull --prefix=backend btcd master`，冲突集中但流程脚本化。
2. **patch-queue（quilt 风格）**：把共识分叉点抽成独立 `.patch`（`patch/01-difficulty.patch`…），
   拉完上游按序 `git apply`，冲突精确定位到具体补丁。
3. **replace 隔离放大**：已用 `replace chaincfg/txscript => ./xxx`——继续扩大"能拆就拆、主程序吃上游版本"。

### 收敛优先级（按收益排序）

1. **netsync/manager.go**（+2650）：压回/跟随上游 → 消除最大冲突源，收益第一。
2. **chainio.go**（+1017）：保留功能，但尽量以上游为基础重做 → 降低长期漂移。
3. **chain.go / blockindex.go / chainview.go**：跟随上游重做。
4. **utxocache / ffldb / thresholdstate / checkpoints**：能并则并、不能则本地小补丁。
5. **共识分叉**（difficulty/validate/merkle/txscript/chaincfg/process/mining）：维持现状，纳入 patch-queue。

## 六、推荐路线 / Roadmap

| 阶段 | 动作 | 产出 |
|------|------|------|
| 现在 | 挂 btcd 上游 remote；建立 §5 收敛清单为同步标准 | 仓库具备同步能力 |
| 近期 | 首个"按需同步"演练：cherry-pick 一个明确想要的修复/特性 | 验证流程 |

| 持续 | 增量式开发风格（新增文件/新增函数，不改上游既有函数） | 控制冲突面 |
| 远期 | 评估向上游提"共识可插拔接口"PR | 可选演进 |

**关键提醒**：当前 fork 依赖版本与上游一致，是"新鲜 fork"；**越早建立"按需同步 + 分叉面收敛"的习惯，每次升级成本越低**。
